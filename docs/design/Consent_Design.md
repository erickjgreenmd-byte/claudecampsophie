# Verifiable parental consent — design, options and open questions

The consent decision in one place, because it accumulated across a conversation on 2026-09-29 and was
making `docs/Owner_Actions.md` #7 unreadable. #7 now points here. Written against code `fc51e39`.

## The rule this all serves

Spec Revision 8, authoritative: *"A parent PIN is a local convenience/step-up mechanism, **not proof of
adulthood or verifiable parental consent**. Integrate a documented verifiable-parental-consent provider
behind an adapter. Store the consent status, purpose/version, provider reference, date and revocation
status; do not store raw identity documents unless expressly necessary and reviewed."*

`AC_ACCESS_02` refuses a production consent state that rests on a checkbox or a PIN. So dropping VPC is not
an option, and "we are parent-first, therefore consent is implied" fails the project's own acceptance
criteria — email plus password verifies an inbox, not an adult.

## Two claims that keep getting merged

| Claim | Established by | Not established by |
|---|---|---|
| This person is an **adult** | A vendor document check against identity databases, or the approved 2023 face-match-to-photo-ID route, or an accepted payment method | A typed date of birth. An Apple ID. A PIN. A pairing code |
| This adult is the child's **parent or guardian** | **The adult's own attestation, captured and versioned** | Nothing in any ID check. No FTC-enumerated method verifies a family relationship, because there is no database of who is whose parent |

Both are required. The regulation contemplates exactly this split: its methods verify the identity and
adulthood of the consenting person, and the relationship rests on their assertion.

## The three methods, ranked for this product

**1. Payment-as-consent** — §312.5(b)(2)'s monetary-transaction method. No added friction, no vendor fee,
and the transaction already happens monthly. Blocked only on the counsel question in `Owner_Actions.md`
#15.

The method does **not** rest on proving adulthood. It rests on the primary account holder being *notified*
of each discrete charge — the theory being that an adult who sees an unexpected receipt objects. Apple does
email a receipt to the Apple ID's address. So the logic holds when the account holder is the adult and
fails exactly when a child holds the account, which is the population COPPA exists for. This is why the
optional Stripe path differs in **kind** and not degree: PencilLift charges that card itself and
notification reaches the cardholder rather than whoever holds the app-store account.

**Verified fact for counsel** (`apps/api/src/services/billing-sync.ts`, `RevenueCatEvent`): the entire
payload PencilLift receives for a store purchase is `id`, `type`, `app_user_id`,
`original_app_user_id`, `aliases`, `product_id`, `store`, `purchased_at_ms`, `expiration_at_ms`,
`price_in_purchased_currency`, `currency`, `period_type`, `offer_code`, `transaction_id`, `cancel_reason`,
`event_timestamp_ms`. **No age, no date of birth, no adult flag, no cardholder name, no Ask-to-Buy
approver.** `app_user_id` is PencilLift's own identifier, generated by PencilLift. No evidence of adulthood
reaches this system from an IAP purchase, so none can be recorded and `status()` has no honest `method`
string to return for it.

Why the parent-first-plus-Apple-ID argument fails at every link: Apple issues children their own Apple IDs
through Family Sharing and those IDs can purchase; Ask to Buy exists *because* children transact; an Apple
ID can be funded by a gift card bought with cash, so no adult payment instrument need be involved; and the
pairing code proves only that the account holder passed a code to a device, which is the same person one
step later. The ordinary failure case: a 12-year-old with their own iPhone and a $50 gift card completes
the whole flow and their homework reaches the model with no adult involved.

**2. k-ID guardian flow** (QR, OTP, email, direct link). Low friction, a per-verification fee, and being
right about the method becomes the vendor's job rather than ours.

`github.com/kidentify/skills`, supplied 2026-09-29, is k-ID's official **Agent Skills** marketplace
(Apache-2.0, 13 skills). Its own README says it encodes integration patterns, not API documentation. So it
is guidance for building the integration — not an SDK, not consent code, and not a contract.

One architectural question first: k-ID's documented flow is `age gate → session → consent → permissions`,
assuming the child arrives first and is classified a minor, while PencilLift is parent-first and
`ConsentProvider.start()` takes `{familyId, adultUserId, policyVersion}` with no child session. Their skill
mentions handling a `challengeId` that arrives without a `sessionId`, so a parent-first path may exist.

**3. Government ID checked against identity databases** — enumerated, strongest, and the one to reach for
last. Two conditions people get wrong: the statute permits it only if the identification is **deleted
promptly** after verification, and *"against databases"* is part of the method — photographing a licence
and looking at it is not it. So it runs through a vendor (Persona, Stripe Identity, Veriff, Jumio, or
k-ID's own) who does the check and the deletion, with PencilLift storing only the reference, the method and
the instant. **Never build a licence-upload endpoint here.**

It ranks last for commercial reasons, not legal ones, and the cost is severe: consent must precede any
child-data collection, so the check lands between signup and the first child profile — at the paywall — and
asking the parent of a six-year-old to photograph a driver's licence to check spelling homework loses a
meaningful share of signups at the moment they were about to pay, at $1–3 per attempt.

All three implement the same `ConsentProvider` interface — `start()`, and `status()` returning
`pending | verified | failed` plus which method verified and when — so the choice is reversible and adding a
second method later is days of work, not a rewrite. A light primary method with an ID check as an
*escalation* is a known pattern, but it is two integrations and is not recommended for launch.

## Recommended signup ordering

Removes a grey area at no cost:

```
1. Sign up                 email + password only. No DOB, no documents
2. "How many children?"    a COUNT only — no names, no ages
3. Show the price          $39.99 + $9.99 × (n-1)
4. Take first payment      Apple / Google / Stripe
5. Verify the adult        vendor; store reference + method + verifiedAt
6. Per child, ONE submission  nickname + grade + age band + the ticked attestation,
                           with its wording version and instant, scoped to that child
7. Issue pairing codes     one per child
8. Child pairs a device    the first moment child data can flow
```

Steps 2 and 6 are the split that matters. `POST /v1/children` takes `nickname`, `gradeLevel` and `ageBand`,
so "list the children" before consent would collect information about identifiable children. Whether that
counts as collection *from a child* is arguable; asking for a count first makes the question moot, which is
cheaper than winning the argument. Step 9 is the unambiguous line and the gate that matters most.

Four corrections to the flow as first proposed: no typed date of birth (a self-declared DOB verifies
nothing and adds sensitive data); never store the licence image; PencilLift does not do the looking; and
verification comes *after* payment, so the per-check fee is not paid for everyone who abandons at the
paywall.

## Scope: per adult, or per child?

The owner proposed (2026-09-29) confirming the adult, then adding each child with a checkbox carrying the
legal statement after each one, then payment, then a code per child. That instinct catches something this
design had wrong, and it splits into two scopes rather than one:

| | Scope | Repeats? |
|---|---|---|
| Adult verification | Per **adult** | Once. A fourth child a year later does not re-verify |
| Attestation + consent scope | Per **child** | Yes — the consent is to the processing of THAT child's data |

`public.consent_records` is family-scoped today (`family_id`, `adult_user_id`), and both
`hasVerifiedConsent` and `consentAllowsChildAccess` read the family's LATEST record. `scope jsonb` exists
and nothing populates it. So as the code stands, a child added a year after signup is covered by an
attestation made when only the earlier children existed — that child was never named in anything the parent
agreed to. **Lead decision: the attestation is per child, and `scope` records which children it covers.**
That is what the column was for.

One refinement on the owner's wording: the child form and its checkbox are **one submission**, not two
steps. Nickname, grade, age band and the ticked statement arrive together, so child details never exist
without an attestation covering them, even momentarily.

## Ordering: verify before payment, or after? — a correction

An earlier note in this project said verify AFTER payment, on the ground that verifying first pays $1–3 for
everyone who then abandons at the paywall. **That reasoning over-weighted the per-check fee and is
withdrawn.** Even at 50% abandonment the cost is $2–6 per converted customer against $40–70 a month in
revenue: recovered inside the first month, and noise.

The real trade-off is different and it has no clean winner:

- **Verify first** — never charge someone you then reject, so no refunds, no chargebacks, no customer who
  was charged and then refused. But asking for a driver's licence before any commitment is a cold ask, and
  a parent who has not yet decided to pay is still browsing. This is where signups are lost.
- **Pay first** — the parent is invested by the time the licence is asked for, so completion is higher. But
  every verification failure becomes a refund, a support ticket and a bad experience.

Which one wins turns on a number PencilLift does not have: **the vendor's verification pass rate.** Ask for
it as part of #7. Above roughly 95%, pay-first is better. Below that, verify-first avoids refund churn.

A hybrid gets both on the Stripe path only: authorise the card, verify, then capture — no charge until
verified. IAP cannot authorise without capturing, so this is web-signup only and does not help an in-app
signup.

## The gap in the schema — needs a forward migration

`public.consent_records` (migration 0001) stores `provider`, `provider_reference`, `method`, `purpose`,
`policy_version`, `scope`, `status`, `verified_at`, `withdrawn_at`, `adult_user_id`. So *how* adulthood was
proved is recorded, and *what* was consented to is recorded — but **the parental-guardian attestation has
no field**, and it is doing real legal work.

**Lead decision:** add it as a forward migration — the attestation's text version and its instant beside
the existing columns — capture it at the consent step on both surfaces, and have counsel approve the
wording as part of #15. Not done on 2026-09-29 because two fix stages were in flight and the migration
number is the lead's to assign when the tree is quiet.

The cases where the attestation is doing all the work, and which no ID check touches:

- A **grandparent, step-parent or foster carer** — all can be legal guardians, and the statute includes
  guardians, so these are legitimate and only the attestation records the claim.
- A **non-custodial parent** consenting over the other parent's objection.
- **Guardian invitations**: several adults can join one family. `adult_user_id` records which adult
  consented, which is right; whether a second guardian joining later owes an attestation of their own is
  undecided, and is a question for counsel rather than for code.
