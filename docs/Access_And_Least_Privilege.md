## In-database roles — the authorization model, for context

Not an access grant to anyone, but the reason production database access is never the right tool: a
request's own Postgres role is the second authorization layer, so even a correct bearer token cannot
reach another family's rows.

`apps/api/src/db.ts` runs every transaction under one of three roles:

| Role | Used for | Set by |
|---|---|---|
| `authenticated` | parent/adult requests | `Db.asParent` |
| `pl_child` | paired-child requests (created by migration `0001_core_identity.sql`) | `Db.asChild` |
| `service_role` | handler code that must bypass RLS and therefore verifies ownership of every referenced row itself | `Db.asService` |

**Dated correction (2026-10-19):** [`API_Inventory.md`](API_Inventory.md) names these roles
`pl_parent`, `pl_child` and `pl_service`. Two of the three are wrong. The code's names are
`authenticated`, `pl_child` and `service_role` (`apps/api/src/db.ts`, `createDb`). The code wins; the
inventory needs the correction applied in its own file.

A Supabase **service-role key** reaches the database as `service_role` and therefore bypasses RLS
entirely. That single fact is why no section below recommends handing one to anybody.

## GitHub — `erickjgreenmd-byte/claudecampsophie`

**Used for:** all source, all records, and all four workflows (CI, `db-migrate.yml`,
`deploy-api.yml`, `deploy-web.yml`). It is the only place credentials for every other service are
stored, as GitHub Actions repository secrets.

### The awkward fact, stated plainly

**The repository is already public** (verified 2026-10-19: `gh api
repos/erickjgreenmd-byte/claudecampsophie --jq .visibility` → `public`, `.private` → `false`).
Read access is not a grant that can be given or withheld — it
already exists for everyone on the internet. A collaborator invitation therefore does not grant
reading; the *only* thing it adds is **write-side capability**. Anybody reasoning about "giving the
contractor read access to the repo" is reasoning about something that has no effect.

A second consequence worth internalising before any grant: the whole handoff packet, these records
included, is world-readable. Nothing here may contain anything that is not safe in public, which is
the rule `scripts/scan-secrets.mjs` enforces (see Credential hygiene).

### Minimum role

| Purpose | Minimum | Why |
|---|---|---|
| (a) Read and understand | **nothing** | Public. Cloning over HTTPS works unauthenticated. |
| (b) Develop | **nothing** | A fork plus a pull request from the fork needs no grant at all. On this repository that is not merely the least-privilege path, it is the only one short of write — see the correction below. |
| (c) Deploy | **collaborator (write)** | `workflow_dispatch` requires write access to the repository, and the workflow must be on the default branch; both hold for the three deploy/migrate workflows. |

**Dated correction (2026-10-19): the graded roles do not exist on this repository.** An earlier
version of this section recommended **Triage** for review-and-propose work. Read, Triage, Write,
Maintain and Admin are the roles GitHub offers on an **organization-owned** repository.
`erickjgreenmd-byte/claudecampsophie` is owned by a **personal account** (`gh api
repos/erickjgreenmd-byte/claudecampsophie --jq .owner.type` → `User`, checked 2026-10-19), and a
personal-account repository has two levels only: the owner, and collaborators, who get push
(write). GitHub's own documentation says collaborators cannot be given read-only access to a
personal-account repository, and points at transferring the repository to an organization if finer
access is wanted.

**So: no collaborator seat at all — fork and pull request — and a collaborator (write) seat only for
whoever must run the deploy workflows, knowing that write is the only seat on offer here and
carries the power described below.** Not Admin either: an admin can change repository visibility,
manage secrets, delete the repository and alter branch protection, and none of that is part of the
engagement — though on a personal-account repository the owner is the only admin anyway. A graded
role such as Triage becomes available only if the owner first transfers the repository to an
organization — **UNDECIDED (owner)**, and unnecessary for the fork-and-PR path.

### What each level can and cannot see

- Everyone (including anonymous): all code, history, Actions **run logs** of a public repository, and
  the two public-by-design values committed in `.github/workflows/deploy-web.yml`
  (`VITE_SUPABASE_URL` and a `sb_publishable_…` key — see Credential hygiene).
- Write: additionally, can push, merge, and **dispatch `deploy-api.yml`, `deploy-web.yml` and
  `db-migrate.yml`, which inject the repository secrets into a job.**
- Nobody, at any role, can read a repository secret's **value** back out of GitHub — but anyone who
  can push to the branch a workflow runs from *and* dispatch it can write a step that prints a
  secret. **Write access to this repository is therefore equivalent in power to holding
  `CLOUDFLARE_API_TOKEN` and `SUPABASE_DB_URL`.** Grant it with that in mind, or grant nothing and
  take pull requests from a fork.
- `ci.yml` declares `permissions: contents: read` and consumes **no** secrets (its only
  secret-adjacent step is `node scripts/scan-secrets.mjs`), so the CI path itself exposes nothing.
- **Neither deploy workflow can target production.** `deploy-api.yml` and `deploy-web.yml` both
  declare `options: [testbed, staging]` on their environment input, so a Write collaborator cannot
  dispatch a production deploy even by accident. That is the workflow agreeing with the runtime: a
  `production` Worker could not boot anyway (`CONSENT_ADAPTERS` is an empty `Set` in
  `apps/api/src/config.ts` and `CONSENT_ADAPTER_FACTORIES` an empty object in `apps/api/src/index.ts`,
  so `providers.consent` can never be `'configured'` and `buildRuntimeOrThrow` returns `NOT_READY`).

### Two things that should exist before any write grant — **UNDECIDED (owner)**

1. **A `main` branch.** There is none. The default branch is `claude/new-session-vil6cz`, and there
   has never been a pull request. Both `ci.yml`'s push filter (`branches: [main, 'claude/**']`) and
   every convention in the records assume a `main` that does not exist.
2. **Branch protection on that branch**, requiring the CI check and at least one review before
   merge. Without it, a Write collaborator pushes straight onto the branch the deploy workflows read
   — which is the exfiltration path described above.

Neither is in place today. Doing them first converts "Write access" from "holds every secret" into
"can propose changes that CI must pass."

### Granting and revoking

- Grant: repository **Settings → Collaborators and teams → Add people**, choose the role.
- Revoke: the same page, **Remove**. Also expect to **rotate every repository secret** afterwards if
  the person ever held Write, for the reason above. Revoking the seat does not un-learn a value a
  dispatched workflow could have printed.
- Audit: the repository's Actions run history shows who dispatched which workflow and when; on a
  public repository that history is world-readable, which is a feature here.

### Safer substitute

Yes, and it is the recommended default: **fork and pull request.** The engineer needs no grant, CI
runs on the PR, and nothing they do can reach a secret: GitHub does not pass Actions secrets to
workflows triggered by a pull request from a fork, and `ci.yml` is triggered `on: pull_request`, not
`pull_request_target` — the trigger that *would* run base-branch workflow code with secrets
available. Two mechanics to expect rather than be surprised by: a first-time contributor's fork PR
needs a maintainer to approve the run, and the fork's `GITHUB_TOKEN` is read-only.

### What the token can and cannot do

- Can: create, overwrite and delete Worker scripts in that account; set and list Worker secret
  *names*; create and edit Hyperdrive configurations — which means it can read the origin connection
  string it was given and point a config at a different database.
- Cannot: see Supabase rows directly, read GitHub secrets, or touch another Cloudflare account.
- Note the coupling: `deploy-api.yml` hands `SUPABASE_DB_URL` to `wrangler hyperdrive create`, so
  **whoever holds the Cloudflare token plus the ability to dispatch that workflow effectively holds
  the database URL.** Scope accordingly.

### Granting and revoking

- Grant: **My Profile → API Tokens → Create Token**, Custom policy as above. The token is shown once.
  Store it as the GitHub repository secret `CLOUDFLARE_API_TOKEN`; add `CLOUDFLARE_ACCOUNT_ID` too if
  the token can see more than one account, which Wrangler needs to disambiguate.
- **Tokens are per-person and independently revocable.** Issue one token per human (and one for CI),
  never a shared one. Revoke from the same API Tokens list — it takes effect immediately and affects
  nothing else.
- Cloudflare account **membership** (a dashboard seat) is a separate, broader grant and is not needed
  by an engineer whose deploys run from CI. Prefer "no seat, one scoped token used by the workflow"
  over "a seat."

### Safer substitute

Partly. `--dry-run` covers everything up to the moment of deploying, so an engineer can be productive
with no token at all. There is no substitute for the final deploy, but `deploy-api.yml`'s `testbed`
environment is the safe target: it runs every provider as a labeled mock and is explicitly marked
**no real child's work may go there** (`apps/api/wrangler.toml`, `[env.testbed]`).

## Credential hygiene

### No secret may enter the repository, and that is enforced rather than hoped for

`scripts/scan-secrets.mjs` is dependency-free and runs in three modes:

| Mode | Where | What it covers |
|---|---|---|
| `--staged` | `scripts/git-hooks/pre-commit` (enable with `git config core.hooksPath scripts/git-hooks`) | the git index, on every commit |
| default (no flag) | `ci.yml`'s "Secret scan" step, and `scripts/verify.sh` (`▸ secrets`) | every tracked file on disk |
| `--artifacts <dir>…` | `scripts/scan-release-artifacts.sh`, CI's last step | **what would actually ship** |

The third mode is the one that matters most, because a secret pasted into a public build variable is
invisible to a tracked-file scan. `scan-release-artifacts.sh` builds the portal, the Worker bundle
(`wrangler deploy --dry-run --env production` — nothing is deployed), the Expo web export and the
public app config that native builds embed, twice (Google Play `production` and Amazon
`production-amazon`), with fake values of the documented public shape in every `VITE_*`/
`EXPO_PUBLIC_*` variable, and scans all of it.

It then runs a **negative control**: it rebuilds the portal and the app config with four fake secrets
planted in public build variables — a service-role JWT, a Stripe test-mode key, an `sb_secret_` key
and a database URL with an inline password — and **fails unless the scan fails and names each
planted detector**. So a build that stops embedding those variables where the scan looks, or a scan
that stops seeing one of them, turns CI red. The fake values are assembled at run time, so no
credential-shaped literal is tracked.

Detector coverage, findings and exit codes are documented in
[`Deployment_Runbook.md`](Deployment_Runbook.md) §3.2 — read that rather than re-deriving it. Two
details worth carrying in your head: **Stripe test-mode keys are secrets here** (this account runs in
test mode, so they are the keys it actually holds), and findings name the file, line, column and
detector but **never the matched value**, because CI logs on a public repository are world-readable.

### Which values are public by design

Only these, and the list is enforced, not conventional — `DOCUMENTED_PUBLIC` in
`scripts/scan-secrets.mjs` (lines 99–103). Read the mechanism precisely before trusting it: the
allow-list is consulted **only in `--artifacts` mode** (`if (artifact && isDocumentedPublic(...))`),
and its job is to stop an *otherwise-detected* value from failing a build scan. It is not a list of
"values the scanner approves of" in tracked-file mode.

| Value | Shape | Why it is public |
|---|---|---|
| Supabase publishable key | `sb_publishable_…` | ships in every client bundle; authority comes from the user's JWT and RLS, not from this key |
| Supabase anon (legacy publishable) key | a JWT whose decoded `role` is `anon` | same |
| RevenueCat public SDK keys | `appl_…`, `goog_…` (**not** `amzn_…` — see below) | compiled into the app binary; a store SDK needs them client-side |

**Dated observation (2026-10-19) — the Amazon public key is on neither list.**
[`Connections.md`](Connections.md) states that an Amazon (Fire tablet) build carries the
`amzn_…` RevenueCat public key in `EXPO_PUBLIC_REVENUECAT_AMAZON_KEY`, so it ships in a client
bundle exactly as `appl_…` and `goog_…` do. But the string `amzn` appears **nowhere** in
`scripts/scan-secrets.mjs`: it is not in `DOCUMENTED_PUBLIC`, whose RevenueCat entry is
`/^(?:appl|goog)_[A-Za-z0-9]+$/`, and it is not in `PATTERNS` either. Nothing fails today, because
no detector matches an `amzn_…` value and so there is nothing for the allow-list to suppress —
`scan-release-artifacts.sh` scans the `production-amazon` app config and passes. The gap is in the
*record*, not the behaviour: the enforced allow-list does not document the Amazon key as public, so
the "public by design" set is narrower in code than in prose. An engineer should not cite
`DOCUMENTED_PUBLIC` as covering three key shapes. Fixing it is a one-line change to that regex and
belongs in its own commit with a test; it is **not** done at HEAD.

Also public, and not secrets: the Supabase project URL, the API base URL, the portal URL, the
`SUPABASE_JWKS_URL` endpoint, the JWT issuer, the Cloudflare account id and a Hyperdrive config id.
`deploy-api.yml` sets the JWKS URL and issuer as Worker *secrets* purely so rotating the project ref
needs no commit; its own comment says neither is a secret.

`VITE_SUPABASE_URL` and a `sb_publishable_…` key are committed in plain text in
`.github/workflows/deploy-web.yml`. That is deliberate and documented in that file's header. It is
also the one place where "public by design" has a cost: **rotating that key means editing that line
and re-deploying the portal**, and because the repository is public, the key is permanently in
history. Treat it as published.

Anything not in the table above is a secret, including every `*_SECRET_*`, `*_API_KEY`,
`SUPABASE_SERVICE_ROLE_KEY`, `CHILD_TOKEN_SECRET`, `HASH_PEPPER`, `DATABASE_URL` and
`SUPABASE_DB_URL`.

### Where secrets live

Nowhere in the repository. Three places only:

1. **GitHub Actions repository secrets** — `SUPABASE_DB_URL`, `CLOUDFLARE_API_TOKEN`,
   `CLOUDFLARE_ACCOUNT_ID`, and optionally `CHILD_TOKEN_SECRET` and `HASH_PEPPER`. This is where the
   runbook's own **dated correction (2026-10-01)** landed: an earlier version said to put the
   database password in the build environment, which both was the wrong place and would not have
   worked, since that container reaches almost nothing outbound and Postgres is not HTTP.
2. **Cloudflare Worker secrets** — set by `wrangler secret put`, listed by name in
   [`Deployment_Runbook.md`](Deployment_Runbook.md) §2. `apps/api/src/config.ts` is the authority on
   which names exist; `apps/api/tests/deploy-secrets.test.ts` proves the deploy path supplies
   everything `loadConfig` refuses to start without.
3. **`apps/api/.dev.vars`** for local `wrangler dev` — gitignored, and a deploy never uploads it.
   Copy `.dev.vars.example`.

### Rotation

| Credential | Rotate by | Catch |
|---|---|---|
| Supabase database password | dashboard → Project Settings → Database → Reset database password | then update the `SUPABASE_DB_URL` GitHub secret **and** the Hyperdrive config, which stores the URL as its origin |
| Cloudflare API token | delete and re-create in My Profile → API Tokens | per-person, so one person's rotation affects nobody else |
| `REVENUECAT_SECRET_API_KEY`, `REVENUECAT_WEBHOOK_AUTH`, `OPENAI_API_KEY`, `RESEND_API_KEY`, `STRIPE_*` | rotate at the provider, then `wrangler secret put` and redeploy | the readiness report flips the matching check to `blocked` while a key is absent, which is the gate working |
| Supabase publishable key | rotate in Supabase, edit the line in `deploy-web.yml`, redeploy the portal | the old value stays in public git history forever |
| **`HASH_PEPPER`** | **do not rotate casually** | it is mixed into stored hashes for PINs and pairing codes. Rotating it silently invalidates every one, and the failures look like a parent mistyping their own PIN. `deploy-api.yml` is written specifically to never overwrite an existing pepper, and to stop the job rather than guess if it cannot read the Worker's secret list. |
| `CHILD_TOKEN_SECRET` | rotating invalidates live child sessions | acceptable, but it logs every paired child out |

### When an engagement ends

1. Remove the GitHub collaborator.
2. If they ever held **Write**: rotate `SUPABASE_DB_URL` (which means resetting the Supabase database
   password) and `CLOUDFLARE_API_TOKEN`. Assume both were readable.
3. Delete their Cloudflare API token, Expo seat, and any provider seat.
4. Leave `HASH_PEPPER` alone unless there is a specific reason to believe it leaked; if it did, the
   consequence is a forced PIN and pairing-code reset for every family, which today is zero families.
5. Record what was rotated, and when, in [`Connections.md`](Connections.md) — configuration names
   only, never values.
