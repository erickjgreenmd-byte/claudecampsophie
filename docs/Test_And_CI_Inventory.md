### The structural tests, honestly

This is the category a contractor will judge hardest, so here is the real shape of it.

**Where it is unavoidable.** `apps/mobile/vitest.config.ts` includes only `src/**/*.test.ts` in a
`node` environment, with the comment "Pure logic only: modules under test must not import
react-native". There are **zero** `.test.tsx` files in `apps/mobile`. So nothing in the phone app is
ever rendered, and the only way the suite can say anything about a screen is to read the screen's
source text. That is what 421 of mobile's 941 tests do. Examples:

- `apps/mobile/src/family/screens.test.ts` asserts `screen('(parent)','home.tsx')` matches
  `/<SignOutButton \/>/`, and that `runtime.ts` matches
  `/signOutParentOnDevice\(\s*effects: ModeEffects = modeEffects,?\s*\)/`. The second is a regex over
  a **function signature**. It protects a shape, not a behaviour: a correct refactor that renames the
  parameter reddens it, and an incorrect one that keeps the name while breaking the call passes.
- `apps/mobile/src/family/contrast.test.ts` (63 tests) walks every `.tsx` under `app/` and `src/`,
  extracts style fills, and requires 4.5:1 against white via `@pencillift/ui-tokens`. This one is
  **better than it looks**: the assertion is a real WCAG property computed from the real token
  values, it generalises to files the original finding never named, and it has an explicit
  `TEXT_FREE_FILLS` escape list. It protects a behaviour (legibility) through a source proxy.

**Where it is a deliberate choice and defensible.** Several structural tests assert things no unit
test can reach because the artifact is configuration, not code:

- `apps/api/tests/guard-call-sites.test.ts` parses every call to `guardChildContent` across
  `apps/api/src` and `packages/domain/src` and requires `evaluateExpressions: true` at every call
  site, with exactly one allowed opt-out (`packages/domain/src/bank/validate.ts`). The behaviour —
  "no child-facing hint may disclose an answer" — cannot be asserted per-call-site any other way,
  because the defect is a *missing* argument at a *new* call site that does not exist yet. This is
  the strongest structural test in the repository.
- `apps/web/src/deploy-config.test.ts` and `apps/api/tests/runtime.test.ts` assert
  `wrangler.toml` contents (`not_found_handling`, Worker names per environment, the absence of a
  `main` entry for the static portal). Each has a failure mode a parent meets and a unit test cannot:
  a wrong `not_found_handling` turns every emailed `/privacy` link into an edge 404.
- `apps/web/src/headers.test.ts` parses `public/_headers` and requires `index.html` to carry no
  inline script, because the CSP forbids one.
- `apps/api/tests/deploy-secrets.test.ts` reads `.github/workflows/deploy-api.yml` and
  `apps/api/wrangler.toml` and requires the two secrets `loadConfig` cannot start without. It exists
  **because of BUG-434**: every deploy the workflow would have produced answered 503 NOT_CONFIGURED
  on every path, `/health` included, and the workflow's own probe step reported that as success. A
  structural test is the only kind that can assert a property of a YAML file.
- `packages/ai/src/cost-doc.test.ts` reads `docs/Cost_Analysis.md` and requires it to agree with
  `AI_STAGES`. A documentation consistency test, correctly labelled as such.

**Where it is weak.** The pattern that will not age well is a regex over a prose string or a
docblock. `apps/mobile/src/family/screens.test.ts` asserts
`/reminders and quiet hours aren’t available yet/i` and `/doesn’t send\s+notifications/` — copy, with
a curly apostrophe, pinned by regex. That is a real requirement (the app must not promise
notifications it cannot send) asserted in the most brittle available way, and there are dozens of
assertions of that species across `apps/mobile` and a handful in `apps/web`
(`ArchivedChildCopy.test.tsx`, `RewardsBalanceStatus.test.tsx`). They will cost a contractor time on
every copy edit and will catch a genuine regression perhaps once.

**Correcting the upper bound.** The file-level figure is **944 across 54 test files** — every test
in every file repo-wide that calls `readFileSync` or `readFile`: `apps/mobile` 421 in 24 files,
`apps/api` 227 in 13, `supabase/tests` 117 in 4, `apps/web` 114 in 9, `packages/ai` 65 in 4, and
none at all in `packages/domain`, `packages/contracts` or `packages/ui-tokens`. An earlier draft
said 809 across 50 files; the grep and the per-file sums give 944 across 54, re-measured
2026-10-19. It still overstates. In `packages/ai`,
65 of 119 tests sit in files that call `readFileSync`, but the structural assertions inside them are
a handful — one `console.log` sweep in `zdr.test.ts`, one docblock-vs-constant check in
`run-metering.test.ts` — and the rest of those files are behavioural. The same is true of
`apps/api/tests/identity.test.ts`, `runtime.test.ts` and `learning-jobs.test.ts`: `identity` and
`learning-jobs` read a source file at exactly one place each (out of 13 and 26 tests), and
`runtime.test.ts` at four (out of 35 — `wrangler.toml`, `.dev.vars.example`, the root `.gitignore`
and a sweep of `src/`), in otherwise integration-driven files. `apps/web` is
the same story, and an earlier draft of this document over-subtracted there: 114 of web's 991 tests
sit in files that call `readFileSync`, but 86 of those 114 are in five `.tsx` files that all render
through `renderPage` — `ArchivedChildSections.test.tsx` has **one** source-reading case out of 53,
and `ArchivedChildCopy.test.tsx` six out of 19. So web's genuinely structural count is about **40**
(the four `.ts` config/source files, plus a dozen cases inside rendering files), not 114, and the
rendered figure in the table is 897 `.tsx` tests less about a dozen. A hand-checked
estimate of **genuinely structural assertions is 450–550, i.e. 6–7% of the suite**, of which roughly
400 are in `apps/mobile` because that package has no other option.

## 3. What runs on what trigger

Four workflows in `.github/workflows/`. **Only `ci.yml` has ever executed**; the three
`workflow_dispatch` workflows have run **zero** times, and nothing is deployed anywhere. There has
never been a pull request on this repository, so the `pull_request` trigger has never fired either —
every CI run so far came from the `push` trigger on `claude/**`.

| Workflow | Trigger | Jobs | What it gates |
|---|---|---|---|
| `ci.yml` | `pull_request`; `push` to `main` or `claude/**` | `verify`, `authorization-postgres-17` | The whole gate, below |
| `db-migrate.yml` | `workflow_dispatch`, input `confirm` must be `APPLY` | `migrate` | Applies all 44 migrations to a hosted Supabase project |
| `deploy-api.yml` | `workflow_dispatch`, `environment` ∈ {testbed, staging}, `confirm` must be `DEPLOY` | `deploy` | Deploys the API Worker |
| `deploy-web.yml` | `workflow_dispatch`, `environment`, `api_base_url`, `confirm` must be `DEPLOY` | `deploy` | Builds and deploys the parent portal |

`concurrency: ci-${{ github.ref }}` with `cancel-in-progress: true` means a push supersedes the
previous run — which is why `docs/Test_Evidence.md` lists several **cancelled** runs that are not
failures.

### `ci.yml` job `verify` (ubuntu-latest, 30 min timeout, `postgres:16` service)

Steps, in order, each a hard gate:

1. `pnpm install --frozen-lockfile`
2. `pnpm format:check` (Prettier)
3. `node scripts/scan-secrets.mjs` — static secret scan of tracked files
4. **Derived documents are current**: `node scripts/dump-api-inventory.mjs --check`,
   `node scripts/dump-open-work.mjs --check`, `node scripts/check-schema-dump.mjs`. CI refuses a
   tree where `docs/API_Inventory.md`, `docs/Open_Work.md` or `docs/schema/schema.sql` has drifted
   from the code it describes. Non-obvious and worth knowing before your first commit: **editing
   `docs/Open_Work.md` by hand fails CI.**
5. `pnpm lint` (`eslint . --max-warnings=0`)
6. `pnpm typecheck` (`tsc -p` per package, workspace-concurrency 2)
7. `pnpm test` — all 7,503, serially, against the Postgres 16 service
8. `pnpm finance:check` — `python3 finance/cost_model.py --check` and
   `finance/promo_school_model.py --check`
9. `node scripts/assert-test-count.mjs` — the anti-vacuity gate
10. `bash scripts/scan-release-artifacts.sh "$RUNNER_TEMP/release-artifacts"` — build what would ship
    and scan it, plus a negative control

### `ci.yml` job `authorization-postgres-17`

A second job on a `postgres:17` service that runs **only** `pnpm --filter @pencillift/db run test`.
Its reason is stated in the workflow: every authorization case was written against PG 16, the hosted
Supabase project runs PG 17.11, and that difference became an untested assumption the moment the
project existed. It prints `select version()` first so the log proves which server was under test,
and it re-implements the floor check inline rather than calling `assert-test-count.mjs`, because that
script audits *every* package with a `test` script and would have failed this job on seven missing
reports rather than on anything about PG 17.

### The anti-vacuity gate

`scripts/assert-test-count.mjs` walks `apps/*`, `packages/*` and `supabase`, and for every package
with a `test` script requires a JSON report with `numTotalTests >= floor`, `numFailedTests == 0`,
and `numPendingTests + numTodoTests == 0`. A green run that executed **zero** relevant tests is a
failure. `apps/api/tests/gate-audit.test.ts` is a self-test of that script, fed synthetic reports
through `PL_TEST_RESULTS_DIR`.

The floors in `scripts/test-minimums.json` currently **equal** the counts exactly
(3670/1224/484/991/941/119/70/4). Two consequences a contractor should price in:

- Deleting or skipping a single test fails CI. That is the point, and it is a genuinely good
  property: `it.skip` cannot be used to get a green.
- **Every commit that removes a test, merges two, or consolidates a file requires editing the floor
  in the same commit.** `docs/Test_Evidence.md` shows earlier floors set to ~95% of the counts; they
  are now at 100%, which removes all slack. Expect this to be the single most common source of a
  surprising red.

### The local gate

`scripts/verify.sh` is the pre-commit gate and runs the same steps in the same order, fail-fast, with
no step piped through a filter that could hide an exit status (lesson L-004). `--only api,db` narrows
to named workspace dirs while others are mid-edit; `--no-tests` and `--no-artifacts` skip those
stages. It additionally runs `node scripts/brand/export-assets.mjs --check`, which CI does not.
`scripts/git-hooks/pre-commit` exists but is not installed by `pnpm install`: the root
`package.json` has no `prepare` script, there is no `.husky` directory and no `.npmrc`, and
`README.md` says nothing about it. Installing it is one manual command, documented in the hook's own
header and in `docs/Access_And_Least_Privilege.md`: `git config core.hooksPath scripts/git-hooks`.
It does prettier and eslint on staged files, a staged-tree typecheck (`scripts/check-staged-tree.sh`,
BUG-034) and `scan-secrets.mjs --staged` — so a fresh clone that skips that command loses all four
until CI runs.

## 4. Overlap and duplication

Genuine redundancy, named.

**(a) Approved pricing is asserted in 39 test files across all five layers.** `3999`/`$39.99`
appears in 39 test files; `9.99` in 24. The layering is partly correct and partly not:

| Layer | File | What it asserts | Verdict |
|---|---|---|---|
| domain | `packages/domain/src/pricing/pricing.test.ts` | `monthlyPriceCents(1..4) === [3999,4998,5997,6996]`; no $9.99 first-child fallback; rejects fractional/negative/over-tier | **The one that matters.** 5 tests, the whole rule. |
| web | `apps/web/src/pages/public/PricingPage.test.tsx` | imports `priceTable()` from the domain, formats it, **then also asserts the literal `['$39.99','$49.98','$59.97','$69.96']`** | Half-redundant. The import makes the page provably derive from the domain; the literal list re-asserts the domain's own test. |
| mobile | `apps/mobile/src/billing/plan-view.test.ts` | hardcodes `'$39.99 per month'`, `storePriceCents: 3999`, and a 2-line prose string naming both prices | **Redundant and brittle.** No import from the domain; the price is a string literal in three places. |
| api | `apps/api/tests/billing.test.ts` + 4 `billing*.review.test.ts` files | `approvedMonthlyCents: 3999`, store-price comparison, `priceCheck: 'matches_approved'` | Mostly legitimate — the *comparison* is API behaviour — but the constant is re-stated rather than imported. |
| db | `supabase/tests/billing_tax.test.ts`, `promotions_schools.test.ts`, `school_report*.test.ts` | `3999` as fixture data inside tax/revenue arithmetic | Fine. This is test data, not a second assertion of the price rule. |

If the owner ever changes a price, the domain test is a one-line edit and the mobile and admin tests
are a sweep of literals across ~20 files. That is the cost of this duplication, and it is real.

**(b) Row-level security is asserted three times.** `supabase/tests/schema_invariants.test.ts`
("every table in the exposed public schema has row level security enabled", a `pg_class` query over
all 44 migrations); `scripts/verify.sh`/CI via that same test; and `db-migrate.yml` runs the
**identical** `relkind in ('r','p') and not c.relrowsecurity` query against the real database. The
workflow comment is explicit that it was deliberately widened from `'r'` to `'r','p'` so the real-DB
check is not weaker than the suite's. This duplication is **justified**: one checks the schema the
suite builds, the other checks the schema that exists. Keep both.

**(c) The secret scan runs four times per CI job.** `scripts/scan-secrets.mjs` on tracked files
(step 3); again inside `scripts/scan-release-artifacts.sh` against four built artifacts; again
against the same artifacts with planted fake credentials as a negative control; and again as
`apps/api/tests/release-gates.test.ts`, which `spawnSync`s the scanner over synthetic artifact
directories (gzip/brotli/zstd variants included) inside the API suite. The negative control is the
valuable one — it proves the scanner still *sees* a test-mode Stripe key and a password-bearing
database URL, which it once did not (noted as LRD-3). The in-suite copy is the most redundant of
the four, but it is also the only one that runs under `--only api`.

**(d) WCAG contrast is asserted in three places.** `packages/ui-tokens/src/index.test.ts` (4 tests,
the token ratios), `apps/mobile/src/family/contrast.test.ts` (63 tests, source sweep over every
phone screen), `apps/web/src/styles.test.ts` (4 tests). The token test is the rule; the two sweeps
are per-surface enforcement of it. Defensible, but the token test is the only one that would survive
a rewrite of either client.

**(e) Copy constants asserted at both ends.** The `.review.test.*` family — 43 files across api,
web, mobile and db — exists because round 4 of the hardening work found cross-surface divergence
(BUG-411 and its successors BUG-421..424). Several of those findings are now asserted twice: once as
"the portal prints the shared constant" and once as "the phone's source contains the same string".
`apps/web/src/pages/app/ArchivedChildCopy.test.tsx` (19 tests) and
`apps/mobile/src/rewards/balance-status.test.ts` are the clearest pair.

## 5. Tests that assert implementation details

Judged per class, on whether it protects a behaviour or a shape. The **Verdict** column is this
review's recommendation and nothing more: every "Delete or replace", "Consolidate" and "Keep" below
is **TENTATIVE** — no owner decision stands behind any of them and no work is scheduled against
them. The classes, the files and what each one asserts are established; what should be done about
them is not.

| Class | Example | Protects | Verdict |
|---|---|---|---|
| Function-signature regex | `screens.test.ts`: `/signOutParentOnDevice\(\s*effects: ModeEffects = modeEffects,?\s*\)/` | shape | **Delete or replace.** A correct rename reddens it; a wrong call keeps it green. The behaviour (device sign-out clears store identity and secure storage) is already asserted by `apps/mobile/src/lib/token-sources.test.ts` and the runtime tests. |
| JSX-element presence regex | `screens.test.ts`: `expect(screen('(parent)','home.tsx')).toMatch(/<SignOutButton \/>/)` | shape | **Unavoidable today**, because `apps/mobile` has no renderer. Would become a one-line render assertion the day the phone app gets one. See [§9](#9-important-behaviour-not-covered). |
| Prose regex with typographic characters | `/reminders and quiet hours aren’t available yet/i` | behaviour, badly | **Consolidate.** Move the string to one exported constant, assert the constant once, and assert that each surface imports it — which is exactly what BUG-411 established and what `IDENTITY_REQUIRED_COPY` failed to do (nothing imported it while its docblock claimed three surfaces did). |
| Docblock-vs-constant agreement | `packages/ai/src/run-metering.test.ts` reads `routing.ts`, finds the budget table in a comment, and compares it to `PROPOSED_STAGE_COST_BUDGET_MICROS` | documentation | Narrow but cheap, and it throws a clear error if the docblock is gone. Keep. |
| `console.log` sweep | `packages/ai/src/zdr.test.ts` greps every file in `packages/ai` for `console.*` | behaviour (no child data in logs) | Keep. The behaviour is "a child's homework never reaches a log line", and a lint rule would be the better home for it. |
| Config-file assertion | `deploy-config.test.ts`, `runtime.test.ts`, `deploy-secrets.test.ts`, `headers.test.ts` | behaviour | **Keep all.** Each has a user-visible failure mode and no other test can reach it. BUG-434 is the proof. |
| Call-site argument sweep | `apps/api/tests/guard-call-sites.test.ts` | behaviour | **Keep.** The defect class is a missing argument at a call site nobody has written yet. |
| Coverage-of-a-set assertion | `screen.test.ts` asserts a minimum case count per safety category before asserting on cases | the test's own validity | Keep. This is the L-054 pattern — a guard over an empty set passes — applied to the test suite itself. |

The honest summary: **the structural tests in `apps/api`, `apps/web` and `packages/ai` are
well-targeted and mostly assert things nothing else can. The structural tests in `apps/mobile` are a
workaround for a missing renderer, and about a third of them assert shapes rather than behaviours.**

The cost driver in `apps/api` is not the assertions; it is `createTestApi` in
`apps/api/tests/helpers.ts`, which for each file creates a **fresh isolated Postgres database**, runs
all 44 migrations plus the Supabase platform shim, and builds a real Hono app with seven labeled
provider mocks. `supabase/vitest.config.ts` and `apps/api/vitest.config.ts` both cap
`maxWorkers: 2` for that reason. It shows up as a package whose wall clock **exceeds** the sum of
its per-file durations, because provisioning happens in the file's hooks and outside the durations
the reporter records: re-measured on 2026-10-19, `supabase/tests` summed 21.6 s of file durations
inside a 48 s wall, and `apps/api` 383.6 s inside a 430 s wall. The pure packages go the other way,
since worker parallelism beats the serial sum — `packages/domain` summed 96.2 s inside a 48 s wall
and `apps/web` 307.6 s inside 215 s. So **neither direction is a rule**: comparing a package's wall
clock with its summed file durations tells you whether workers or per-file provisioning dominates,
and in this repository it is provisioning for `api` and `db` and parallelism for everything else.

This is the right trade. A suite that mocked the database would be fast and would not have found any
of the RLS, `search_path`, deadlock or clock defects in the ledger. But it means **the API suite's
cost scales with the migration count**, and there are 44 migrations with more coming.

## 7. Flakiness

Three incidents, all investigated to a mechanism rather than closed as flakes. The procedural rule
that came out of them (lesson **L-081**) is one of the more valuable things in this repository: *when
one case in a thousand reds under load and passes alone, measure the suspected input across hundreds
of values before the word "flake" is used.*

**BUG-429 — not a flake; a 13% product defect.** One case in 1,203 reddened under full-repo
contention and passed on every isolated re-run (14 of them). Measuring instead of shrugging found
that `generateCandidates` seeds itself with the practice-set key, which contains the child's random
UUID, and a cross-call duplicate was discarded with nothing redrawing — so for **13.25% of children**
a skill's pool held 3 candidates instead of 4, and the weak part of their daily set could place only
one question on the skill they were actually failing. Fixed by giving `generateSkillItems` an
`avoid` set. Regression: `packages/domain/src/bank/bank.test.ts`, "a child's id must not decide how
many questions their weakest skill gets", 40 fixed seeds asserting an identical per-skill count map.
**Residual the ledger states honestly:** the final fix rests on a draw budget, and
`grammar.plural_nouns` has exactly four words at grade 1 — about `(3/4)^48` per constrained draw.
That is a probability, not a proof, and growing the word pool is content work nobody has done.

**BUG-431 — a true test-infrastructure defect.** `apps/web/src/pages/app/ArchivedChildCopy.test.tsx`
enumerates every source file and reports which ones import four copy constants. Twice, each time on
the **first** suite run in a freshly started container, it reported an empty importer list for a
constant `HomeworkPage.tsx` plainly imports. An empty list is indistinguishable from the real
regression the test exists to detect, so the red asserted something false about the product. A probe
ran the scan 300 times and found a stable 386-file set with zero deviation, which rules out the scan
and leaves the file tree not yet fully readable at that moment — stated in the ledger as the likely
mechanism, **not** as a proven one. Fix: `importersOf` now goes through `scannedFiles()`, which
refuses to answer unless the sweep reached the three files the expectations name. Proved by mutation.
Lesson **L-083**: a sweep that proves absence must first prove it looked. The ledger's own follow-up
— *"every other test in the repo that proves a NEGATIVE by sweeping the file tree deserves the same
precondition"* — is **partly done, not unresolved**, and an earlier draft of this document repeated
the ledger row's closing sentence instead of reading the tests. Of the 14 test files that drive a
sweep from `readdirSync`, six already assert that the sweep found something before asserting what it
did not find:

| File | Its precondition |
|---|---|
| `apps/mobile/src/privacy/data-practices.test.ts` | the file list must contain `(parent)/_layout.tsx` and `(child)/_layout.tsx` |
| `apps/mobile/src/monetization/child-navigation.test.ts` | a whole case, `'finds the child routes it is guarding'`, requiring `_layout.tsx` and `home.tsx` |
| `apps/mobile/src/brand/BrandMark.test.ts` | a case, `'finds the route screens'` (≥ 20), plus every `OWNED_ELSEWHERE` name must still exist |
| `apps/mobile/src/family/screens-r2.review.test.ts` | `screens.length > 8` and `loading.length > 5` |
| `apps/mobile/src/family/contrast.test.ts` | every named source must yield at least one style fill |
| `apps/api/tests/guard-call-sites.test.ts` | `calls.length >= 2`, and `optOuts` must *equal* the allowed-opt-out set — an empty sweep fails both |
| `apps/api/tests/family-hardening-r4.review.test.ts` | `updates.length > 0` before the filtered list must be empty |

So `apps/api/tests/guard-call-sites.test.ts` is **not** an example of the gap; it is one of the
better-guarded sweeps in the repository. The files that still prove a negative with no precondition
are `apps/api/tests/pg-client.test.ts`, `apps/api/tests/runtime.test.ts`,
`packages/ai/src/zdr.test.ts`, `apps/mobile/src/navigation.test.ts`,
`apps/mobile/src/lib/token-sources.test.ts` and `apps/mobile/src/rewards/review.test.ts`. Each would
pass vacuously on an empty file list.

**BUG-083 — an ordinary test race, fixed.** CI run #18 at `b6e9998` is the only **red** CI run
`docs/Test_Evidence.md` records: one web sponsor-card viewability test, reproduced locally 1 in 12
under CPU load. It is **not** the only red run the branch has had. The live Actions history for
`claude/new-session-vil6cz` holds 127 runs, and run **#122** at `b239f53` (id `36906695674`,
2026-10-01 18:25 UTC, "Add a deployable mock-backed testbed…") failed in `verify` at the step
"Tests (unit + real-Postgres authorization)" while `authorization-postgres-17` passed. That run has
no row in `docs/Test_Evidence.md`. Nothing here says what it was — the record simply stops short of
it, and a contractor pricing this work should read the two together rather than either alone. The mechanism was established from the libraries (Testing Library's `findBy` resolves after a
real `setTimeout(0)` while React flushes the passive effect later), not guessed. Fixed in `48430c5`.

**No test in this repository is marked skipped, retried, or quarantined.** `assert-test-count.mjs`
would fail the build if one were.

## 8. Obsolete

Little, and what there is is labelled.

- **A branch that cannot be reached, and a test that correctly does not assert it.**
  `CONSENT_ADAPTERS` in `apps/api/src/config.ts` is an **empty `Set`**, and it alone decides the
  value: `consentProvider()` (same file) returns `{ consent: 'configured' }` only for a
  `CONSENT_PROVIDER` name that set contains, so `providers.consent` can never be `'configured'`.
  `buildRuntimeOrThrow` (`apps/api/src/index.ts`) then returns NOT_READY —
  `{ code: 'BLOCKED_EXTERNAL' }`, served as HTTP 503 — for `APP_ENV=production`, on an explicit
  branch that requires both `providers.consent === 'configured'` **and**
  `providers.storage === 'supabase'`, before any provider is selected.
  `CONSENT_ADAPTER_FACTORIES` in `apps/api/src/index.ts` is an empty object too, but it is the
  *second* lock, not the cause: it is only read inside `selectConsentProvider`'s `'configured'`
  branch, which production never reaches, and an unknown adapter name is NOT_CONFIGURED in every
  environment (`apps/api/tests/runtime.test.ts`, "production without a consent adapter refuses to
  serve" and "an unknown adapter name is a configuration error in every environment").
  `apps/api/tests/config.test.ts` handles the analogous identity case
  explicitly and says so in a comment: it asserts that the **configuration fails**, not what the
  unreachable branch returns, because "asserting the returned value instead would be asserting dead
  code — proved by mutating that branch to return the mock, which changed nothing observable
  (L-054)". This is the correct treatment of a not-yet-implemented adapter, and it is worth copying.
- **Owner decision #45 superseded a design, and the tests moved with it.** The safety design once
  had a family hold, an operator email and parent actions; the owner decided the parent is the sole
  recipient. The old paths were removed in migration 0790 and the test surface was rewritten
  (`supabase/tests/parent_flag_review.test.ts`, `apps/api/tests/safety-flag-email.test.ts`). No
  tests for the withdrawn design remain.
- **BUG-244's recovery path was deliberately removed** after round 6 and the defect reopened as an
  accepted open defect (see `docs/Open_Work.md`). Its tests went with the code.
- **The one thing a contractor should check rather than trust:** several `.review.test.*` files are
  named for hardening *rounds* (`hardening_r1_db`, `hardening_r1_db2`, `hardening_r2_db`,
  `hardening_r5_db`, `billing-r2`, `jobs-r2`, `mobile-r2`, `family-hardening-r4`). The naming is
  chronological, not functional, so a reader cannot tell from the filename what any of them covers,
  and two round files for the same area (`hardening_r1_db` and `hardening_r1_db2`) is a sign of
  append-only growth rather than organisation. Nothing in them is dead; they are just filed by date.

## 9. Important behaviour not covered

This is the most valuable section and the shortest to state: **the suite has never met a real device,
a real provider, a real photograph, a real browser, or a real deploy.** 7,503 tests pass in a node
process with labeled mocks, against a Postgres container, and that is the entire evidence base.
`docs/Test_Evidence.md` says so in its own first paragraph. What that leaves unprotected, per area:

**The phone app — the largest gap.** `apps/mobile` has 941 tests and **zero** of them render a
single React Native component. There is no Detox, no Maestro, no simulator run, no EAS build. What
is therefore completely untested:

- That the app **compiles and launches** on a device or simulator. Nothing in CI builds it natively;
  `scripts/scan-release-artifacts.sh` runs `expo export --platform web`, which is a different
  bundler target and does not exercise native modules.
- The camera. `apps/mobile/src/homework/scan-screen.test.ts` reads the screen's source; nothing has
  ever opened a camera, taken a frame, or handled a permission denial.
- Secure storage (`expo-secure-store`), push/notification permissions, deep links, the Expo Router
  navigation tree as the router actually resolves it, app-state transitions, and offline behaviour.
- Store billing. `apps/mobile/src/billing/store.test.ts` is the second-slowest mobile file (49 tests,
  1.2 s) and runs entirely against a store mock. No App Store, Play or Amazon sandbox purchase has
  ever been made; see `docs/Connections.md`.
- iPad layout and the Amazon Appstore channel, both of which have brand/config tests and no device.

**AI and homework — the product's core loop, untested end to end.** `packages/ai` is 119 tests
against `createMockResponsesClient` and a fake `fetch`. No request has gone to OpenAI. In
consequence:

- **No real photograph of homework has ever been through this system.** The whole grading path —
  extraction, rubric, prompt-key agreement, protected parent solutions, feedback — is exercised with
  synthetic text fixtures in `apps/api/tests/scan-process.test.ts` and
  `packages/domain/src/grading/*`. Real-world failure modes (glare, skew, handwriting, a dense
  ten-page worksheet, a page photographed upside down) are unprotected. BUG-096 and the
  grading-retry gap in `docs/Open_Work.md` are already the visible edge of this.
- Real model output shape. The schemas in `packages/ai/src/schemas.ts` are asserted against
  hand-written fixtures. A live model that returns a field the `strictObject` schema rejects is
  exactly **BUG-420**, an accepted open defect: 97 response schemas in `packages/contracts` are
  `z.strictObject` and **throw** on an unknown key, so adding a response field breaks every
  already-installed app build. No test can catch that, because no test has two versions.
- ZDR. `checkChildDataGate` refuses every under-13 request for want of documented approval, and that
  refusal is well tested. What is untested is the path *after* approval exists, because it does not.
  BUG-430 is the record of a privacy page that asserted a ZDR agreement which does not exist.

**Deployment and the hosted database.** `db-migrate.yml`, `deploy-api.yml` and `deploy-web.yml` have
run **zero** times. Queried live on 2026-10-19, the Supabase project (`pencillift-staging`) reports
`PostgreSQL 17.11` and **zero tables** across `public`, `private` and `app` — and `private` and `app`
do not exist as schemas at all, only `public` does, so the count is zero because the schema was never
created rather than because it was emptied. Two leftover probe artifacts do sit on it (schema
`probe_tmp`, trigger `probe_sessions_trg` on `auth.sessions`), both confirmed present by the same
query, and `db-migrate.yml` drops both (its "Remove the capability probe" step). So:

- No migration has ever been applied to a real Supabase project. `authorization-postgres-17` is a
  good proxy — it is the reason that job exists — but a container is not a managed service with
  Supabase's own roles, extensions and pooler.
- Hyperdrive, the Worker's only binding, has never been created. The `wrangler.toml` placeholder
  substitution in `deploy-api.yml` has never run against a real account.
- The SPA fallback (`not_found_handling`) is asserted from `wrangler.toml` text and has never served
  a request. A parent opening an emailed `/privacy` link has never been tried.
- **Production cannot boot at all**, by construction: `CONSENT_ADAPTERS` is empty, so
  `buildRuntimeOrThrow` returns `BLOCKED_EXTERNAL` and the Worker answers **503 on every path**,
  `/health` included (see [§8](#8-obsolete) for the exact branch). Only `testbed` and `staging` are
  deployable. **Staging, by contrast, does boot** — an earlier draft of this document said it
  answers 503 NOT_CONFIGURED, and that is wrong. `apps/api/tests/runtime.test.ts` asserts three
  times over that "staging should build": staging gets a consent provider named `not_configured`
  with `isMock: false`, an equally unavailable billing provider, and unavailable storage and email
  unless their keys are set — each a real adapter that **rejects when called**, not a mock and not a
  boot failure. So a staging deploy would serve requests and fail at the first call into a provider
  that has no credentials, while `productionReadiness()` (`apps/api/src/config.ts`) reports the
  deployment blocked on consent, identity, billing, AI, ZDR evidence and the rest. Nothing in the
  suite can tell you what `APP_ENV=production` does once an adapter exists, because the code path
  has no implementation to run.

**The browser.** 991 jsdom tests are not a browser. Untested: real CSS layout and the responsive
breakpoints, actual focus and keyboard order, screen readers, the CSP as a browser enforces it
(`headers.test.ts` asserts the file, not the enforcement), `IntersectionObserver` and image decoding
as implemented rather than as stubbed by `FakeImage`/`FakeOffscreenCanvas`, and anything
cross-browser.

**The portal-to-API boundary, which no test crosses.** `apps/web/package.json` does not depend on
`@pencillift/api` and nothing under `apps/web/src` imports it or `createApp` — verified by grep —
so the contract between portal and Worker is held entirely by the shared types in
`@pencillift/contracts` plus `tsc`. `apps/web/src/test/render.tsx` builds a complete `ApiClient`
object literal, typed against `@pencillift/contracts/client`, for every page test: the type is
shared, the runtime behaviour is not. A response body that satisfies the type but that the real
Worker never sends, a status code the portal mishandles, a CORS preflight, an auth-token refresh
across the boundary — none of these is exercised anywhere, in either package.

**Providers, all of them.** Stripe, RevenueCat, App Store, Play, Amazon, Resend, Supabase Storage,
Supabase Auth admin and OpenAI are each replaced by a labeled mock built in
`apps/api/src/providers/` or faked at `fetch`. Webhook signature verification, retry and
idempotency behaviour, real tax computation, real refund and chargeback shapes, and real email
deliverability are all unexercised. `docs/Provider_Capability_Matrix.md` is the per-provider record.

**Load, concurrency and the clock at scale.** `apps/api` caps at `maxWorkers: 2`; nothing measures
throughput, connection-pool behaviour under Hyperdrive, or job-dispatcher contention with more than a
handful of rows. Domain code takes `now` as input and is well tested across time zones
(`packages/domain/src/scheduling/local-time.test.ts`), but no DST transition has been observed in a
running system.

## 10. Assessment

**Is this suite worth its cost? Yes for about 60% of it by measured test count, and the expensive
parts are the good parts.** The five rows below are the ones this review will defend by name, and
they are what the share is computed from: 484 + 1,224 + ~1,571 + 1,268 + ~30 = **~4,577 of 7,503,
i.e. 61%** — 60% if [§2](#2-categorisation)'s narrower ~1,180 integration figure is used instead of
the whole `apps/api` package. Anything above that comes from the unit and rendered-UI rows, which
this review judges sound but did not enumerate, so a reasonable reviewer lands anywhere between
**60% and 80%**. The share is a **judgement, not a measurement**; an earlier draft of this section
said "roughly 70%" without showing the arithmetic, which did not survive a recount.

What earns its keep, in order of confidence per second of CI:

1. **`supabase/tests` (484 tests, 35 s).** Real Postgres, real `SET LOCAL ROLE`, real
   `request.jwt.claims`, real RLS, nothing mocked. `schema_invariants.test.ts` alone — RLS on every
   `public` table, no client role privileges in `private`, `search_path` pinned on every
   `SECURITY DEFINER` function — generalises automatically to every future migration. For a product
   holding children's homework this is the single highest-value thing in the repository. **Keep
   entirely; add to it first.**
2. **`apps/api` integration (1,224 tests, 166 s).** Expensive, and the expense buys the only
   evidence that routes, policies, jobs and entitlements agree. It found the deadlock (BUG-106), the
   clock defect (BUG-090) and most of the authorization findings. **Keep.**
3. **`packages/domain` property tests (~1,571 of 3,670, 29 s).** `fast-check` over pricing,
   entitlements, grading, rewards, promotions and the question bank. Cheap per test and found
   BUG-429, a real 13%-of-children product defect that example tests had passed over for the whole
   life of the function. **Keep, and extend the shape-invariant pattern L-081 describes.**
4. **The safety corpus (1,268 tests, 1.8 s).** It reads as padding — 17% of the suite from one file —
   and it is not. It is a classifier with seven recall passes and six false-positive passes recorded
   against it in the ledger, and a classifier's test suite *is* its corpus. 1.8 s for 1,268 cases is
   the cheapest coverage here. **Keep.**
5. **The config- and workflow-assertion tests (~30 tests).** BUG-434 — every deploy producing a
   Worker that could not start, with the workflow reporting success — was found by an adversarial
   reading, not by a test, and the test that would have caught it now exists. **Keep all of these.**

What I would consolidate — every item below is **TENTATIVE**: a proposal from this review, with no
owner decision behind it and no work scheduled:

- **The 171 prose-regex assertions** across `apps/mobile` and `apps/web`. Counted, not estimated:
  the 28 source-reading test files in those two packages hold **390** `toMatch(/…/)` assertions
  against file text, of which 171 match copy (English words, no code punctuation) and 219 match code
  shape. Move each string to one exported constant, assert the constant's content once, and assert
  that each surface *imports* it. That is already the established pattern (BUG-411) and it is applied
  unevenly. This cuts maintenance materially without losing a single real guarantee.
- **The pricing literals in ~20 files.** Import `priceTable()`/`monthlyPriceCents()` instead of
  restating `3999` and `'$39.99 per month'`. Keep the domain test as the single statement of the rule.
- **The 48 function-signature and JSX-presence regexes in `apps/mobile`** (counted: 18 match a
  `<Component`, 30 match a declaration or a typed parameter list) — but only *after* the package can
  render. Deleting them before that leaves the phone app with nothing. Note the narrowness of that
  48: on the wider reading of "pins a code shape rather than a behaviour" the figure is **219**,
  because most of the rest pin a JSX prop, a ternary or a call expression rather than a signature.
- **`apps/api/tests/release-gates.test.ts`'s overlap** with `scripts/scan-release-artifacts.sh`. Keep
  the negative control; the in-suite duplicate is the third copy of the same scan.
- **Raise the floors off 100%.** Setting `test-minimums.json` to the exact counts means every
  consolidation above requires a floor edit in the same commit. ~95% (which is what
  `docs/Test_Evidence.md` shows earlier rounds using) keeps the anti-vacuity guarantee and removes
  the friction.

What I would add, in priority order — and this is where a contractor's money should go, not into more
unit tests. These are **TENTATIVE** too: none of them is an owner decision, a scheduled task or a
requirement, and items 2–4 all need owner credentials or accounts that do not exist yet
(`docs/Owner_Actions.md`):

1. **One rendered test harness for `apps/mobile`.** It is the highest-leverage change available.
   ~400 structural tests become real assertions, and the single largest untested surface in the
   product (every phone screen, and the child's entire experience) gets its first behavioural
   coverage.
2. **A device smoke path**: an EAS build, launch, pair a child, open the camera, take one synthetic
   page, see a result. One run of that would produce more new information than the next thousand
   unit tests.
3. **One real homework photograph, end to end, against a real model.** The product's core loop has
   never been observed. Expect it to find several defects on the first attempt; BUG-096 and the
   grading-retry gap predict where.
4. **Run `db-migrate.yml` against the staging project.** 44 migrations, never applied to a managed
   Postgres. The `authorization-postgres-17` job was built precisely because this is an untested
   assumption, and the job is a proxy, not the thing.
5. **A forward-compatibility test for BUG-420.** Parse a response containing one unknown field with
   each of the 97 `strictObject` schemas. It will fail, which is the point: the defect is accepted
   and open, and a test makes the day it bites a red rather than a support ticket.
6. **The L-083 precondition on the six sweep-proves-absence tests that still lack one** —
   `apps/api/tests/pg-client.test.ts`, `apps/api/tests/runtime.test.ts`,
   `packages/ai/src/zdr.test.ts`, `apps/mobile/src/navigation.test.ts`,
   `apps/mobile/src/lib/token-sources.test.ts` and `apps/mobile/src/rewards/review.test.ts`. The
   ledger names this as unfinished work; six of the fourteen sweeps have it already, listed in
   [§7](#7-flakiness), so this is a half-day of copying an established pattern, not new design.

The one-sentence verdict: **this is not hundreds of generated tests.** It is a disciplined suite
whose expensive half (real Postgres, real app, property-based domain checks) is genuinely
load-bearing and whose cheap half contains a well-identified maintenance liability of 171 prose-regex
and 48 signature- or JSX-shape assertions (219 source-text pins in all), concentrated in the one
package that has no renderer. What should worry a contractor is not the suite's quality but its
**blind spot**: every test passes
in a node process, and the product has never met a device, a provider, a photograph or a deploy.
