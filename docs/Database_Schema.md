## 1. How to read this

The schema is **defined entirely by the 44 numbered files in `supabase/migrations/`**. There is no
ORM, no declarative schema file and no dashboard-authored DDL. `docs/schema/schema.sql` is what the
44 files produce; it is derived and regenerated, never edited.

`supabase/scripts/migrate.ts` is the only applier:

- `listMigrations()` reads the directory, keeps `*.sql`, and sorts **lexicographically** — the same
  ordering the Supabase CLI uses. Numeric prefixes make lexicographic order equal numeric order.
- `applyMigrations()` then runs each file **in its own transaction** (`sql.begin` → `tx.unsafe(text)`),
  in order, and throws `Migration <name> failed: …` naming the file that failed. One file is therefore
  all-or-nothing; the set is not.
- There is **no migration ledger table**. Nothing records which files have been applied, and every
  one of the 97 tables is created with a plain `create table` (none use `if not exists`). The set is a
  one-shot build against an empty database. Re-running it against an already-migrated database fails
  on the first `create table`. Any future incremental deploy needs either a ledger or a hand-chosen
  file list — **TENTATIVE: no such mechanism exists or has been designed.**

Three consumers apply the same script, so the tested schema and the hosted one are built by one code
path rather than two. They are not yet known to be identical: the hosted project has never had the
script run against it, so **TENTATIVE / UNVERIFIED — that the result is the same on hosted Supabase
holds only until `db-migrate.yml` has run once** (§12 lists what is untested and the one hosted
capability that was probed). The three consumers:

| Consumer | Path |
|---|---|
| The authorization test suite | `supabase/tests/harness.ts` → `createTestDb()`: creates a throwaway database per test file, loads `supabase/tests/shim/supabase_platform_shim.sql`, then `applySelectedMigrations` |
| The committed DDL dump | `scripts/dump-schema.sh` → scratch database, shim, `pnpm --filter @pencillift/db run migrate`, `pg_dump --schema-only -n public -n private -n app` |
| The hosted project | `.github/workflows/db-migrate.yml` → `pnpm --filter @pencillift/db run migrate` against `secrets.SUPABASE_DB_URL` |

**The hosted project has none of this schema.** A Supabase project exists (`pencillift-staging`, ref
`uroolgscjkbpcsioqogm`, us-west-1, PostgreSQL 17.11, organization on the Pro plan at roughly
25 USD/month) and the migrations have never been applied to it: zero tables in `public`, `private` or
`app`. `db-migrate.yml` has run zero times. Nothing is deployed — no Worker, no portal, no native
build. See §12.

### What is NOT in this schema

- **`auth`** belongs to Supabase Auth (GoTrue). The migrations read it and add one trigger to it; they
  never define it. `pg_dump` excludes it, so `docs/schema/schema.sql` does not show it. §10 states
  exactly what the application expects of it; `supabase/tests/shim/supabase_platform_shim.sql`
  emulates it for tests.
- **`storage`** belongs to Supabase Storage. Migration `0100` inserts one bucket row and one policy
  into it (§11); the shim emulates it.
- **Extensions.** `0001` creates `pgcrypto`, `btree_gist` and `citext`. `pg_dump -n public` omits
  `CREATE EXTENSION`, so **`docs/schema/schema.sql` alone will not build**: it references
  `public.citext`, `public.gen_random_bytes` and a GiST `EXCLUDE` constraint whose operator class comes
  from `btree_gist`. Build from `supabase/migrations/`, which is the source of truth anyway.
  Note that `0001_core_identity.sql:6-8` writes `create extension if not exists …` with **no `schema`
  clause**, and the migrations name the extension objects **unqualified** (`gen_random_bytes` at
  `0001_core_identity.sql:77`, `citext` at `:179`). Which schema each lands in, and what the stored
  default and the column type end up qualified as, therefore depend on the applying session's
  `search_path` — locally that is `public`, which is why the committed dump says `public.citext` and
  `public.gen_random_bytes`. **TENTATIVE / UNVERIFIED on hosted Supabase:** where the platform already
  provides an extension in a schema of its own, the `if not exists` line is a no-op and the unqualified
  reference resolves through the platform's search path instead, so the hosted objects can be correctly
  built and still not match the committed dump's qualification. Nothing has been applied there, so this
  is untested either way (§12). It is not hypothetical for one of the three: `pencillift-staging`
  already carries `pgcrypto` in schema `extensions` (queried 2026-10-19 — `pg_extension` there holds
  `pgcrypto`, `pg_stat_statements` and `uuid-ossp` in `extensions`, `plpgsql` in `pg_catalog`,
  `supabase_vault` in `vault`), so `create extension if not exists pgcrypto` will be a no-op and
  `gen_random_bytes` will resolve to `extensions.gen_random_bytes`, not `public.`. `btree_gist` and
  `citext` are **not** installed there, so those two will be created by `0001` and land wherever that
  session's `search_path` puts them. Expect the hosted qualification of `gen_random_bytes` to differ
  from the committed dump; that is a dump-comparison artifact, not a build failure.

## 2. Schemas and the rule each embodies

| Schema | Created by | Exposed through PostgREST | Rule |
|---|---|---|---|
| `public` | Nothing here — the Supabase platform (and any bare PostgreSQL database) already provides it. No migration contains `create schema public`; `0001` only grants `usage` on it to `pl_child` (`0001:23`) | Yes | Everything a client may ever see, with row-level security on **every** table and column-level grants narrower than the policies. |
| `private` | `0001` | **No** | Secrets and material no client may read at any granularity: credential hashes, parent worked solutions, answer keys, serve state, rate-limit counters, operational scratch. |
| `app` | `0001` | No (holds no tables) | The authorization and guard vocabulary. Every RLS predicate, every trigger body and every `SECURITY DEFINER` helper lives here, so a policy is one function call and the rule has one definition. |

### Why a child can never read `private`

Three independent mechanisms, each tested:

1. **No schema `USAGE`.** `0001`: `revoke all on schema private from public;` then
   `grant usage on schema private to service_role;` — and nothing else. `anon`, `authenticated` and
   `pl_child` hold no `USAGE` on `private`, so they cannot name an object in it at all.
2. **No object privileges.** `grant all on all tables in schema private to service_role` and
   `alter default privileges in schema private grant all on tables to service_role`. Later migrations
   (`0710`, `0770`) grant individual `private` tables to `service_role` only, and `0770` additionally
   revokes `private.deployment` from `service_role` before granting it back `select` alone.
3. **Not reachable through the Data API.** Supabase exposes only `public`, and `pl_child` is never
   granted to the PostgREST authenticator (`docs/Architecture.md` §4), so a child token cannot reach
   PostgREST in the first place; the API sets `set local role pl_child` on its own connection.

`supabase/tests/schema_invariants.test.ts` pins (1) and (2) in *no client role holds privileges in the
private schema*: `information_schema.role_table_grants` for `private` with grantee in
`anon`/`authenticated`/`pl_child`/`PUBLIC` must be empty, **and** `has_schema_privilege` for `USAGE`
must be false for all three.

`private` tables carry **no RLS policies and RLS is not enabled on them** — deliberately. RLS would be
redundant where no client role holds a privilege, and `service_role` is `BYPASSRLS` anyway. The
invariant that every table has RLS applies to `public` only, by its own query
(`n.nspname = 'public'`), and the same predicate is re-run against the real database in
`db-migrate.yml`.

### The role model

| Role | Created by | What it is |
|---|---|---|
| `anon` | Supabase platform (shim in tests) | Unauthenticated. Holds no privilege anywhere in this schema beyond `USAGE` on `app`. |
| `authenticated` | Supabase platform | A signed-in **adult**. Claims come from a Supabase access token. |
| `service_role` | Supabase platform (`BYPASSRLS`) | The API's own identity. Bypasses RLS; still bound by triggers and CHECKs. |
| `pl_child` | `0001`: `create role pl_child nologin noinherit` | A paired child's session. **Not** a Supabase auth user; the child token is not a Supabase JWT. Granted `USAGE` on `app` and `public` and a hand-listed set of **column-level** `SELECT`s (§9). |

Role creation tolerates an existing role (`exception when duplicate_object or unique_violation`)
because roles are cluster-wide and several test databases are built concurrently.

## 3. Tables by area, in migration order

Format per table: purpose, then columns as `name type` with notable defaults in parentheses, then
primary key, foreign keys, notable CHECK constraints. `ts` abbreviates `timestamptz`
(`timestamp with time zone`). Unless a foreign key says otherwise it has **no** referential action —
see §3.0.

### 3.0 A property that holds across the whole schema: almost nothing cascades

Of 186 foreign keys, **three** carry `ON DELETE CASCADE` and **six** carry `ON DELETE SET NULL`. The
other 177 have no referential action:

| Constraint | Action |
|---|---|
| `identity_declarations_family_id_fkey` → `families(id)` | `CASCADE` |
| `identity_verifications_family_id_fkey` → `families(id)` | `CASCADE` |
| `support_case_messages_case_id_fkey` → `support_cases(id)` | `CASCADE` |
| `deletion_requests_child_fkey` → `child_profiles(id, family_id)` | `SET NULL (child_id)` |
| `support_cases_period_fkey` → `billing_periods(channel, provider_period_id)` (`0810:51-52`) | `SET NULL` |
| `ops_settings_updated_by_fkey`, `safety_reports_parent_action_by_fkey`, `safety_reports_feedback_id_fkey`, `support_cases_assignee_user_id_fkey` | `SET NULL` |

If you count these yourself with `select confdeltype, count(*) from pg_constraint where contype = 'f'`
you will see **four** `CASCADE`, not three. The fourth is `auth.sessions.sessions_user_id_fkey`, which
belongs to `supabase/tests/shim/supabase_platform_shim.sql:37` — test scaffolding emulating GoTrue,
not this schema. Filter on `nspname in ('public','private','app')` to get the 186 this page counts.

Every other row is deleted explicitly, in a fixed order, by `app.purge_family_data()` (§7). That is
the design: deletion is an audited operation with a per-table count, not a side effect of a cascade.
It also means **any new table holding family data must be added to that function by hand**, or a purge
will leave its rows behind (or fail on the foreign key).

A second property: **composite family-scoped foreign keys**. Child-owned tables reference
`child_profiles(id, family_id)` rather than `child_profiles(id)`, and subject-owning tables reference
both `child_subjects(id, family_id)` and `child_subjects(id, child_id)`. A row therefore cannot name
child A with a subject belonging to child B, even on a direct Data-API insert (migration `0850`,
finding DB-R1-05). The `*_id_family_id_key` unique constraints exist only to be the targets of those
composite keys.

### 3.1 Core identity — migration `0001_core_identity.sql`

**`public.families`** — one household; the tenancy root of nearly every other table.
`id uuid` (`gen_random_uuid()`) · `display_name text` · `timezone text` (`'America/New_York'`) ·
`billing_ref text` (`'fam_' || encode(gen_random_bytes(12),'hex')`, unique) · `created_by uuid` ·
`created_at ts` (`now()`) · `updated_at ts` (`now()`) · `deletion_requested_at ts` ·
`deleted_at ts` · `inactivity_notified_at ts` (added by `0680`).
PK `id`. Unique `billing_ref`. FK `created_by` → `auth.users(id)`.
CHECK: `display_name` 1–80 chars; `timezone` 1–64 chars (the real IANA check is a trigger, §7).
`deleted_at` is the **tombstone**: `app.family_is_active()` and `app.is_family_member()` both require
it to be null, so tombstoning a family revokes every adult's and child's access in one update.

**`public.family_memberships`** — which adults belong to a family and in what role.
`id uuid` · `family_id uuid` · `user_id uuid` · `role text` · `status text` (`'active'`) ·
`invited_by uuid` · `accepted_at ts` (`now()`) · `revoked_at ts` · `revoked_by uuid` ·
`created_at ts` (`now()`) · `last_seen_at ts` (added by `0680`; the API stamps it at most daily).
PK `id`. FKs `family_id` → `families(id)`; `user_id`, `invited_by`, `revoked_by` → `auth.users(id)`.
CHECK: `role in ('owner','guardian')`; `status in ('active','revoked')`; `(status = 'revoked') =
(revoked_at is not null)`.
Three partial unique indexes enforce the household shape (§5), and `app.enforce_adult_limit()` caps
active adults at two (§7).

**`public.guardian_invitations`** — a pending invitation for a second adult.
`id uuid` · `email public.citext` · `family_id uuid` · `invited_by uuid` · `status text`
(`'pending'`) · `expires_at ts` · `accepted_by uuid` · `accepted_at ts` · `created_at ts` (`now()`).
PK `id`. FKs `family_id` → `families(id)`; `invited_by`, `accepted_by` → `auth.users(id)`.
CHECK `status in ('pending','accepted','revoked','expired')`. `citext` makes the address
case-insensitive, which matters because the API compares it with the accepting adult's **verified**
auth email via `app.adult_auth_email()`.

**`private.guardian_invitation_tokens`** — the invitation token, hashed.
`invitation_id uuid` · `token_hash bytea` (unique) · `created_at ts` (`now()`).
PK `invitation_id`. FK → `guardian_invitations(id)`. Private because the plaintext token is a bearer
credential; only its hash is ever stored.

**`public.consent_records`** — verifiable parental consent events, one row per event.
`id uuid` · `family_id uuid` · `adult_user_id uuid` · `provider text` · `provider_reference text` ·
`method text` · `purpose text` · `policy_version text` · `scope jsonb` (`'{}'`) · `status text` ·
`is_test_provider boolean` · `verified_at ts` · `withdrawn_at ts` · `created_at ts` (`now()`).
PK `id`. FKs `family_id` → `families(id)`; `adult_user_id` → `auth.users(id)`.
CHECK: `status in ('pending','verified','failed','withdrawn')`; `status='verified'` requires
`verified_at`; `status='withdrawn'` requires `withdrawn_at`; `scope` must be a JSON object or array.
`is_test_provider` is the column that lets the readiness gate tell a mock consent from a real one.

**`private.parent_pins`** / **`private.child_pins`** — PIN verifiers, never PINs.
`parent_pins`: `user_id uuid` PK → `auth.users(id)` · `pin_hash text` · `failed_attempts integer`
(`0`, `>= 0`) · `locked_until ts` · `updated_at ts` (`now()`).
`child_pins`: `child_id uuid` PK → `child_profiles(id)`, same four columns.

**`private.adult_unlocks`** — a step-up ("prove you are the adult") bound to one auth session.
`id uuid` · `user_id uuid` → `auth.users(id)` · `auth_session_id text` · `method text` ·
`created_at ts` (`now()`) · `expires_at ts` · `revoked_at ts`.
PK `id`. CHECK `expires_at > created_at`; `method in ('pin','biometric','password')`.
Read only through `app.has_recent_adult_unlock()`, which is what the step-up RLS policies call. The
`auth.sessions` trigger revokes unlocks when their session ends (§7, §10).

**`public.child_profiles`** — a child, by nickname and grade only. No legal name, no birth date.
`id uuid` · `family_id uuid` · `nickname text` (1–40) · `grade_level smallint` (0–12) ·
`age_band text` · `status text` (`'draft'`) · `accessibility jsonb` (`'{}'`) ·
`curriculum_notes text` (≤2000) · `created_at ts` · `updated_at ts` · `archived_at ts` ·
`attestation_version text` · `attested_at ts` · `attested_by uuid` (the last three added by `0970`).
PK `id`. Unique `(id, family_id)`. FKs `family_id` → `families(id)`; `attested_by` → `auth.users(id)`.
CHECK: `age_band in ('5-7','8-10','11-13','14-18')`; `status in ('draft','active','archived')`;
`accessibility` object-or-array; `child_profiles_attestation_complete` — the three attestation columns
are all null or all set; `child_profiles_active_requires_attestation` — `status <> 'active'` or
`attested_at is not null`. A child cannot become active without a recorded guardian attestation.
Column comments on the three attestation columns explain the versioning (see `docs/schema/schema.sql`
and `docs/design/Consent_Design.md`).

**`public.child_devices`** — a paired tablet or browser.
`id uuid` · `family_id uuid` · `child_id uuid` · `label text` (1–60) · `platform text` ·
`paired_at ts` (`now()`) · `last_seen_at ts` · `revoked_at ts`.
PK `id`. FKs `family_id` → `families(id)`; `(child_id, family_id)` → `child_profiles(id, family_id)`.
CHECK `platform in ('ios','android','web')`.

**`private.child_pairing_codes`** — the one-time code a parent reads out to pair a device.
`id uuid` · `family_id uuid` · `child_id uuid` · `code_hash bytea` (unique) · `created_by uuid` ·
`created_at ts` (`now()`) · `expires_at ts` · `consumed_at ts` · `failed_attempts integer` (`0`).
PK `id`. FKs `family_id` → `families(id)`; `(child_id, family_id)` →
`child_profiles(id, family_id)`; `created_by` → `auth.users(id)`. CHECK `expires_at > created_at`.
A partial unique index plus `app.child_pairing_codes_before_insert()` guarantee at most one live code
per child (§5, §7).

**`public.child_sessions`** — a live child session.
`id uuid` · `family_id uuid` · `child_id uuid` · `device_id uuid` · `created_at ts` (`now()`) ·
`expires_at ts` · `revoked_at ts` · `revoke_reason text`.
PK `id`. FKs `family_id` → `families(id)`; `(child_id, family_id)` → `child_profiles(id, family_id)`;
`device_id` → `child_devices(id)`. This row is what `app.current_child_id()` validates on **every**
child query.

**`private.child_refresh_tokens`** — rotating opaque refresh tokens, hashed.
`id uuid` · `session_id uuid` → `child_sessions(id)` · `token_hash bytea` (unique) ·
`issued_at ts` (`now()`) · `expires_at ts` · `used_at ts` · `replaced_by uuid` (self-reference).
PK `id`. Any re-presentation of a rotated token revokes the session; there is no recovery column —
see §12 on migration `0880`.

**`public.admin_users`** — the owner's own staff.
`user_id uuid` PK → `auth.users(id)` · `role text` · `created_at ts` (`now()`) · `revoked_at ts`.
CHECK `role in ('owner_admin','support')`. `app.is_owner_admin()` additionally requires the caller's
`aal` claim to be `aal2`, so admin reads need MFA.

**`public.audit_events`** — append-only audit log.
`id bigint` **GENERATED ALWAYS AS IDENTITY** · `family_id uuid` · `actor_user_id uuid` ·
`actor_kind text` · `action text` (1–100) · `target_type text` · `target_id text` ·
`metadata jsonb` (`'{}'`) · `created_at ts` (`now()`).
PK `id`. FKs `family_id` → `families(id)`; `actor_user_id` → `auth.users(id)`.
CHECK `actor_kind in ('parent','child','admin','system','provider')`; `metadata` object-or-array.
`audit_events_append_only` (`app.prevent_mutation`) refuses every UPDATE and DELETE. The migration
comment is explicit that this table holds pseudonymous identifiers and statuses only — never homework,
answers or child content.

### 3.2 Learning — migration `0100_learning.sql`

**`public.child_subjects`** — the six subjects plus parent-named custom ones, per child.
`id uuid` · `family_id uuid` · `child_id uuid` · `subject_key text` · `display_name text` (1–60) ·
`enabled boolean` (`true`) · `created_at ts` (`now()`).
PK `id`. Unique `(id, family_id)`, `(id, child_id)`. FKs as usual.
CHECK `subject_key in ('math','reading','spelling_vocabulary','grammar_writing','science',
'social_studies','custom')` — the six approved subjects, plus `custom`.
Unique index on `(child_id, lower(display_name))`.

**`public.test_dates`** — an upcoming test, per subject.
`id uuid` · `family_id uuid` · `child_id uuid` · `subject_id uuid` · `test_date date` ·
`scope_notes text` (≤2000) · `created_at ts`.
PK `id`. Unique `(subject_id, test_date)`. FKs to `families`, `child_profiles(id, family_id)` and
**both** `child_subjects(id, family_id)` and `child_subjects(id, child_id)`.

**`public.study_materials`** — spelling lists, notes, passages.
`id uuid` · `family_id uuid` · `child_id uuid` · `subject_id uuid` · `kind text` ·
`content_text text` (≤20000) · `storage_path text` · `created_at ts`.
PK `id`. Same four FKs. CHECK `kind in ('spelling_list','study_guide','taught_notes',
'reading_passage')`; at least one of `content_text`/`storage_path` is not null.

**`public.learning_schedules`** — one row per child; when daily sets and the weekly review land.
`child_id uuid` PK · `family_id uuid` · `review_weekday smallint` (`4`, 1–7) ·
`review_local_time time` (`16:00`) · `review_questions_per_subject smallint` (`8`, 4–20) ·
`schedule_version integer` (`1`, `>= 1`) · `daily_local_time time` (`15:30`) ·
`daily_question_count smallint` (`5`, 3–10) · `paused_from date` · `paused_to date` ·
`quiet_hours_start time` · `quiet_hours_end time` · `child_reminders_permitted boolean` (`false`) ·
`updated_at ts`.
CHECK: `paused_from`/`paused_to` both null or both set, `paused_to >= paused_from`.
`schedule_version` is bumped by two triggers (§7) so a regenerating job can tell its plan is stale.
Local times are `time without time zone`, resolved against `families.timezone`.

**`public.assignments`** — a homework scan, with the processing state machine.
`id uuid` · `family_id uuid` · `child_id uuid` · `subject_id uuid` · `status text` (`'draft'`) ·
`idempotency_key text` (8–200, unique) · `created_by_kind text` · `page_count smallint` (`0`, 0–50) ·
`processing_attempts smallint` (`0`) · `error_code text` · `created_at ts` · `updated_at ts` ·
`uploads_closed_at ts` (added by `0710`).
PK `id`. Unique `(id, family_id)`, `idempotency_key`. FKs to `families`,
`child_profiles(id, family_id)`, and both subject composites.
CHECK `status in ('draft','uploading','queued','extracting','checking','verifying','ready',
'needs_rescan','needs_parent_review','failed_retryable','failed_final','cancelled','deleted')`;
`created_by_kind in ('parent','child')`.
The CHECK lists the states; `app.guard_assignment_transition()` enforces which transitions are legal
and makes `deleted` terminal and immutable (§7).

**`public.source_pages`** — one uploaded page, by storage path.

**`public.reward_redemptions`** — the request workflow.

`cancelled_by in ('child','parent')`.

(**`<> 0`**) · `idempotency_key text` (3–200) · `reason text` (≤300) ·

### 3.6 Operations: deletion, jobs, notifications, safety, exports — `0600_operations.sql`

**`public.deletion_requests`** — the tombstone-first deletion record.

`kind in ('scan_process','daily_set_generate','thursday_review_generate','review_top_up',

**`public.notification_devices`** — a device that may receive a push.

`created_at ts`.

`resolution_note text` · `transcription_at ts` (`0760`) · `screen_categories text[]` (`0760`) ·

`resolution text` (`0760`/`0790`) · `parent_action_at ts` (`0790`) · `parent_action_by uuid`
(`0790`, `ON DELETE SET NULL`) · `parent_emailed_at ts` (`0790`) ·

`category in ('unsafe_content','wrong_or_confusing','upsetting','answer_revealed','other',

`status in ('open','triaged','escalated','resolved')`;
`parent_email_status in ('sent','not_sent','failed')` and `(= 'sent') = (parent_emailed_at is not
null)`; `resolution in ('false_match','addressed')` and only on a `resolved` report, with
`false_match` reserved to `system` reports; a linked question or hint requires a `child_id`;

`family_visible` is the "hold from the family" mechanism from `0760`. Per the owner decision of

deliberately rather than removed. The lead's dissent is recorded in `docs/Threat_Model.md`.

### 3.8 Monetization, catalog and revenue (spec P16) — `0640_monetization.sql`

Parent-facing only: nothing in this area is ever shown to a child. `0640` creates fifteen tables —

exception is `public.family_monetization_prefs`, whose single policy
`family_monetization_prefs_member_read` is `SELECT TO authenticated`.

the caller is a family member, the child exists in that family, the child is **not archived**, and no
open deletion covers it — then rejects control characters in free text and applies a per-family hourly
row bound, counting the family's rows in the **sliding hour** before the write: 60 test dates, 60
study materials, 80 rewards, 20 support cases (parent-opened only), 60 support replies
(parent-authored only), and for subjects 40 **extra** rows — the first row of each
`(child_id, subject_key)` pair in the hour is free, because `GET /children/:childId/subjects` creates
a child's six defaults on an unlimited read path, so a bound counting them flatly would refuse a
legitimate family.

Each bound is exactly **twice** the matching API rule — `subjectCreatePerFamily` 20,
`testDateCreatePerFamily` 30, `studyMaterialCreatePerFamily` 30, `rewardCreatePerFamily` 40 in
`apps/api/src/middleware/rate-limit.ts`, and 10 cases / 30 replies an hour in
`apps/api/src/routes/support.ts:41-42`. Twice is the right factor because the API limiter is
**fixed-window** (`app.rate_limit_hit`, migrations `0610`/`0720`), which can legitimately pass one
whole rule's worth at the end of one window and another at the start of the next — so no request the
API allowed is refused here. That is verified by reading both numbers against each other, and
`supabase/tests/hardening_r2_db.test.ts:626` exercises the bound; it has not been measured against
real traffic. The bounds' job is only to stop one Data-API statement writing hundreds of rows. The
reasoning is written out at length in the function body (`0860_hardening_r2_db.sql:181-195`) — read it
before changing a number.

### Purges and pruning — the deletion machinery

`app.purge_family_data(p_family uuid, p_child uuid default null) returns jsonb` (**DEFINER**, granted
to `service_role` only). Takes `families FOR UPDATE`; for a family purge requires the family to be
**tombstoned first** (`P0001` otherwise), for a child purge requires an open child-scoped deletion
request. Then it sets `pencillift.purging = 'on'` **transaction-locally**, which is what
`app.purge_in_progress()` reads to lift the append-only guards, and deletes table by table in
dependency order, returning a JSON object of per-table row counts (which is what lands in
`deletion_requests.purge_report`). It also collects the storage paths the caller must remove from the
bucket, and deletes job rows whose **payload** mentions the child, its assignments or its exports.
Redefined three times: `0620` created it, `0710` extended it, `0820` added the support-case deletes to
the family branch (a child purge leaves support cases: they are the parent's text).

`public.request_deletion(uuid, uuid)` (**DEFINER**, granted to `authenticated` and `service_role`) —
files the deletion, revokes sessions and devices, cancels queued jobs, marks assignments deleted,
tombstones the family, revokes memberships, settles exports and enqueues the purge job, in one
transaction. Redefined by `0620`, `0710`, `0840`, `0890`, `0920`, `0930` and `0960`. The reason it
keeps growing is worth understanding before touching it: **it is granted to `authenticated`, so the
Supabase Data API can call it with a parent's own access token and never reach the Hono handler**.
Each of those migrations moved one more effect out of the handler and into the function. `0930`
additionally fixed its lock order (slot assignment before child profile) to match every other writer
of that pair.

`app.inactivity_delete_family(uuid, timestamptz, timestamptz, timestamptz)` (**DEFINER**, service-role
only) — the second writer of a family-scope deletion. Requires a notice to have been sent and not
superseded by later activity, and **refuses to delete a family that may still be charged**
(`app.family_may_be_charged`). Takes the clock as a parameter rather than calling `now()`. The
single-argument form from `0680` was dropped by `0710`.
**UNDECIDED: the inactivity period itself.** The `0680` header states that the mechanism ships
disabled behind the API flag `INACTIVITY_DELETION_ENABLED` (read at
`apps/api/src/config.ts:251`) and that *"12 months is the spec's proposal, not an approved policy"*.
See `docs/Owner_Actions.md`.

Pruning (all **DEFINER**, service-role only): `purge_ended_auth_sessions(integer)`,
`purge_expired_rate_limit_buckets(timestamptz, integer)`, `prune_terminal_jobs(interval)`,
`prune_session_rows(interval)`, `prune_credential_rows(interval)`.

## 9. RLS policies

**All 79 `public` tables have RLS enabled.** No table uses `FORCE ROW LEVEL SECURITY`, so
`service_role` (`BYPASSRLS`) is unaffected — the API's own connection is bounded by triggers, CHECKs
and the function grants above, not by policies.

87 policies. Every one names its role explicitly (`TO authenticated` or `TO pl_child`); **no policy
is granted to `anon`**, so an unauthenticated caller sees nothing anywhere.

**Policies are the outer bound, not the whole bound.** Column-level grants are narrower than every
policy. `0860` revoked `insert, update` on `child_profiles` from `authenticated` and `insert` on
`safety_reports`, so the `child_profiles_member_insert`, `child_profiles_member_update` and
`safety_reports_parent_insert` policies below describe a path the **grants** now close for the
Data API; those writes go through the API. Read a policy together with the grants in §2 and §7.

### The one trigger on an `auth` table

```
create trigger pencillift_auth_session_ended
  after delete on auth.sessions
  for each row execute function app.auth_session_ended();
```

Defined by `0720_identity_hardening.sql`. `app.auth_session_ended()` is `SECURITY DEFINER` with a
pinned `search_path` and is revoked from `public`, `anon`, `authenticated` and `pl_child`. On each
delete it: inserts `(old.id, old.user_id, now())` into `private.ended_auth_sessions`
(`on conflict do nothing`); revokes every unexpired `private.adult_unlocks` row bound to that
`auth_session_id`, so a step-up cannot outlive the session that earned it **including on the PostgREST
path**, whose step-up policies call `app.has_recent_adult_unlock()`; and calls
`app.purge_ended_auth_sessions(8)` so the table stays bounded even if no scheduled purge runs.
GoTrue deletes the `auth.sessions` row on local, global and "others" sign-out and on expiry, so one
trigger covers all of them.

**Whether the hosted migration role may create it is the one hosted capability that has been
probed, and it passed.** `docs/Owner_Actions.md` #20 records it as answered on 2026-10-01 by running
it on `pencillift-staging` before any migration: `create trigger … after delete on auth.sessions`
succeeded, and a `security definer … set search_path = ''` function reading `auth.sessions` returned a
count rather than a permission error — which is why `probe_sessions_trg` is still on that table (§12).
So `0720` and `0830` are expected to apply. That probe covered `auth.sessions` and nothing else: the
`app`/`private` schemas, `create role pl_child`, the three extensions, the `storage` writes of `0100`
and the sequence revokes were **not** probed (§12).

**This trigger is the schema's single write into Supabase's own territory.** It must survive a
Supabase platform upgrade that recreates `auth.sessions`, and nothing in the repository checks that it
still exists on a running project. **TENTATIVE: no monitoring for it exists or has been designed.**

## 11. Storage buckets

### What the migration creates

`0100_learning.sql` inserts one bucket row and one policy into Supabase's `storage` schema:

```
insert into storage.buckets (id, name, public, file_size_limit, allowed_mime_types)
values ('homework', 'homework', false, 15728640,
        array['image/jpeg', 'image/png', 'image/heic', 'application/pdf'])
on conflict (id) do update set public = false;
```

| Property | Value |
|---|---|
| Bucket id / name | `homework` |
| Public | **`false`**. The `on conflict (id) do update set public = false` clause re-asserts it whenever `0100` is applied — but the set is one-shot and not re-runnable (§12), so on any one database that is the first application and there is no later one. An accidental dashboard flip to "public" is **not** reverted by anything that runs today |
| File size limit | 15728640 bytes (15 MiB) — the same ceiling as `source_pages.byte_size` |
| Allowed MIME types | `image/jpeg`, `image/png`, `image/heic`, `application/pdf` — the same list as `source_pages.mime_type` |

One policy on `storage.objects`:

```
create policy homework_parent_read on storage.objects
  for select to authenticated
  using (bucket_id = 'homework'
         and app.is_family_member(app.try_uuid((storage.foldername(name))[1])));
```

The object path's **first segment is the family id**, and an adult may read an object only if they are
an active member of that family. `app.try_uuid()` returns null rather than raising on a non-UUID
segment, so one malformed object path cannot make every policy-filtered storage query error.

There is **no insert, update or delete policy** on `storage.objects`: uploads and deletes go through
API-issued signed URLs under the service role.

**TENTATIVE / UNVERIFIED — whether either statement is permitted on a hosted project.** Both objects
belong to Supabase Storage, not to the role that applies migrations: on hosted, `storage.buckets` and
`storage.objects` are owned by the storage service's own role, and `CREATE POLICY` requires ownership
of the table. Neither the `insert … on conflict` nor the `create policy` has ever been run there —
nothing has been applied (§12) — and the owner-action-#20 probe covered `auth.sessions` only
(`docs/Owner_Actions.md` #20). If either is refused, `0100` fails whole, the run stops with `0001`
applied and nothing after it, and the schema is left part-built (§1: one transaction per file, not one
for the set).

### What the application expects — `apps/api/src/providers/supabase-storage.ts`

The adapter takes `supabaseUrl`, `serviceRoleKey`, an optional `bucket` (**default `'homework'`**),
`fetchImpl`, `clock` and `timeoutMs`, and calls these endpoints under `${supabaseUrl}/storage/v1`:

| Operation | Request |
|---|---|
| Signed upload | `POST /object/upload/sign/{bucket}/{path}` → `{ url }` |
| Signed download | `POST /object/sign/{bucket}/{path}` with `{ expiresIn }` → `{ signedURL }` |
| Exists | `HEAD /object/{bucket}/{path}` |
| Stat | `GET /object/info/{bucket}/{path}` → `{ size, content_type, etag, … }` |
| Remove | `DELETE /object/{bucket}` with `{ prefixes: [...] }`, batched at 1000 |

Object key shape, from the `0100` comment on `source_pages.storage_path`:
`{family_id}/{child_id}/{assignment_id}/{page_id}.{ext}`.

Two behaviours an implementer needs to know, both documented in the adapter's own header:

- Signed upload URLs have a **server-fixed two-hour lifetime**. A shorter requested lifetime is
  reported honestly as the real expiry rather than pretending the URL expires sooner.
- `stat` reports the **measured size only**. The info response carries the S3 ETag, which is an MD5
  for single-part uploads and not a content digest at all for multipart ones; there is no SHA-256, so
  verifying `source_pages.sha256` would mean downloading every page. The registered hash is therefore
  **not** re-checked against storage.

**TENTATIVE / UNVERIFIED, stated in the file's own header:** the adapter is *"UNTESTED AGAINST A LIVE

## 12. Migration reconciliation

This is the question an external engineer actually needs answered, so it is answered flatly, with the
evidence for each claim.

### Are all migrations committed?

**Yes.** `git status --porcelain` at `70d352c` shows no modification, addition or deletion under
`supabase/`. The 44 files in `supabase/migrations/` are all tracked and all committed. There are no
untracked `.sql` files, no `*.sql.bak`, and no migration directory other than
`supabase/migrations/`.

### Is the schema reproducible from the migrations alone?

**Yes, onto an empty PostgreSQL 16 or 17 database that already has the Supabase platform objects** —
with one caveat and one dependency, and **only where "the platform objects" means the test shim.** Both
reproductions that have actually happened (CI's `verify` job on `postgres:16`, its
`authorization-postgres-17` job on `postgres:17`) run against a bare container that the job owns and
that carries no platform-issued grant, no managed `postgres` role and no pre-installed extension
(`.github/workflows/ci.yml`; `supabase/migrations/0910_sequence_public_revoke.sql` says the same of
CI in its own prose). Reproducibility **on hosted Supabase**, where migrations run as a managed
non-superuser `postgres` and platform objects and grants already exist, is therefore
**TENTATIVE / UNVERIFIED**. What is and is not known about it:

| Hosted capability `0001`/`0100` need | Status |
|---|---|
| `create trigger … on auth.sessions`, and a `SECURITY DEFINER` function reading it (`0720`, `0830`) | **Probed and succeeded** on `pencillift-staging`, 2026-10-01 — `docs/Owner_Actions.md` #20 |
| `create schema app`, `create schema private` (`0001:10-11`) | **Not probed** |
| `create role pl_child` (`0001:19`) | **Not probed.** Related refusals are on record: the managed `postgres` role may neither change its own password nor grant itself to a new role (`docs/Connections.md`) |
| `create extension` for `pgcrypto`, `btree_gist`, `citext` (`0001:6-8`) | **Not probed**, and the schema each lands in is search-path dependent (§1) |
| `insert into storage.buckets`, `create policy on storage.objects` (`0100:452-460`) | **Not probed**; both objects are owned by the storage service, not by the migration role (§11) |
| That the revokes in `0870`/`0910`/`0940` actually remove what a platform role granted | **Cannot be true in general** — a revoke removes only what the running role granted, and reports success either way; see the enforcement table below |

Any one of those being refused fails that file whole and stops the run with the earlier files applied
— the set is not transactional (§1), so the database is left part-built and, since there is no ledger,
not resumable without a hand-chosen file list.

- `supabase/scripts/migrate.ts` applies the 44 files in lexicographic order, one transaction per file.
  The same code path builds (a) a throwaway database per test file in the authorization suite, (b) the
  committed DDL dump, and (c) the hosted project when `db-migrate.yml` runs. There is no second
  implementation.
- **Dependency:** the migrations reference `auth.users`, `auth.sessions`, `storage.buckets`,
  `storage.objects`, `storage.foldername()` and the roles `anon`, `authenticated`, `service_role`. On a
  real Supabase project the platform provides them. Off-platform,
  `supabase/tests/shim/supabase_platform_shim.sql` provides them — **test scaffolding, not product
  schema**, which is why `scripts/dump-schema.sh` dumps only `public`, `private` and `app`.
- **Caveat:** the set is **not idempotent and not re-runnable.** All 97 tables use plain
  `create table` (0 use `if not exists`) and there is no migration-ledger table, so a second run
  against an already-built database fails on the first statement. Applying the schema is a one-shot
  operation per database today. **11 of the 44 files carry an executable `DROP`:** 10 of them write it
  literally (`0620`, `0650`, `0670`, `0710`, `0760`, `0790`, `0830`, `0850`, `0900`, `0950` —
  constraints, policies, triggers, one index, one function, and two `alter column … drop not null` /
  `drop constraint … , add constraint …` forms), and `0800` is the eleventh, issuing its drops through
  `execute format` (`0800:66`). That eleven is the figure the `db-migrate.yml` header cites, and it is
  why that header explains at length that the Supabase MCP connector cannot be used: it times out on
  every statement containing `DROP`. A plain `grep -ciE '\bdrop\b' supabase/migrations/*.sql` reports
  **12** files, not 11 — the twelfth is `0990`, whose only match is prose in a comment
  (`0990:8`).

  has **zero tables in `public`, `private` and `app`** — and in fact the `private` and `app` schemas

  zero relations and zero functions across those three schemas; `pg_namespace` holds `public` and
  `probe_tmp` and neither `private` nor `app`; `pg_roles` holds no `pl_child`. The organization is on
  the Pro plan, roughly 25 USD/month.
- `.github/workflows/db-migrate.yml` has run **zero times**. It is `workflow_dispatch`-only and
  refuses to proceed unless its `confirm` input is the literal string `APPLY`.
- Nothing is deployed anywhere: no Worker, no portal, no native build. The deploy workflows have run

### Were there manual dashboard changes?

**Two probe artifacts, and nothing else known.** They are the only divergence **recorded** between the
hosted project and the migration set — recorded in `docs/Owner_Actions.md` #20, `docs/Connections.md`
and `docs/Access_And_Least_Privilege.md`, not read off the database by anything in this repository:

| Artifact | What it is |
|---|---|
| schema `probe_tmp` | Left by the owner-action-#20 capability probe |
| trigger `probe_sessions_trg` on `auth.sessions` | Same probe. Its function returns `OLD` and writes nothing |

They were left in place because **removing them is itself a `DROP`, which the connector that created
them cannot issue** (the same MCP limitation described above). `db-migrate.yml` removes both as a
build step, after applying the migrations and before the run ends:

```
drop trigger if exists probe_sessions_trg on auth.sessions;
drop schema if exists probe_tmp cascade;
```

They are harmless (the trigger function is a no-op) but have no business on a database about to hold
real rows. No product object was ever created by hand on the hosted project — there are none at all.

Two details worth having before that run, neither of them a blocker:

- The drop step is named for the probe only, so it cannot touch `0720`'s own trigger: it names
  `probe_sessions_trg` and leaves `pencillift_auth_session_ended` on the same table. It runs **after**
  the migrate step, so if a migration fails the step is skipped (there is no `if: always()`) and both
  artifacts stay.
- **The probe's trigger function lives inside `probe_tmp`, so the two drops are sufficient.** Queried
  on the project on 2026-10-19: `probe_sessions_trg` on `auth.sessions` fires `probe_tmp.t()`, and
  `probe_tmp` holds no relations. `drop schema probe_tmp cascade` therefore takes the function with it
  and no third leftover survives. (Nothing in the repository records this — it was read off the
  project, so re-check it rather than trusting this line if anyone has touched the project since.)
  The verification is two queries, before and after the run: `select nspname from pg_namespace`, and
  the `auth`-schema trigger list joined to `pg_proc`.

`0880_child_refresh_idempotency.sql` existed and was **deleted, not reverted**. It added a nullable

| Check | Where | What it would catch |

| The same check, against the **real** database | `db-migrate.yml`, after applying | the hosted schema diverging from the rule |

At `70d352c`: **7,503 tests pass across 8 packages, zero skipped**, and the floors in
`scripts/test-minimums.json` equal the actual counts exactly.

**What that table does not enforce, and an external engineer should price in.** Every row but one runs
inside `schema_invariants.test.ts`, against a database CI built seconds earlier, and such a database
carries no privilege granted by anyone but the migrations themselves. Two consequences, both written
out in `supabase/migrations/0910_sequence_public_revoke.sql`:

- A `revoke` removes only a privilege granted by the role running it (or by a role it is a member of).
  A `PUBLIC` grant issued by a platform role before this schema was deployed renders in `relacl` as
  `=wU/<that role>` and survives every statement in `0870`, `0910` and `0940` — **which report success
  anyway**, no error and no warning, so the deploy looks clean with the privilege still held
  (`supabase/tests/hardening_r2_db.test.ts:1392` pins exactly that behaviour on a planted non-grantor
  grant). On hosted Supabase migrations run as a managed, non-superuser `postgres`, so this is the
  realistic case, and CI cannot see it.
- So "no client role holds a privilege on a `public` sequence" is **established for every database CI
  or `dump-schema.sh` builds, and UNVERIFIED for the hosted project.** Confirming it there means
  running the query from the `[HR4-0860-01] no client role holds a privilege on a sequence in public`
  case (`supabase/tests/schema_invariants.test.ts:319`) against the deployed database and inspecting
  each sequence's `relacl` for a bare-grantee entry; repairing a hit takes a revoke issued by the
  grantor, which the migration role may not be able to issue at all.

The same reservation applies to the one row that does run against the real database: `db-migrate.yml`
re-runs the *RLS* predicate there, and nothing else. The per-schema table counts the workflow's final
step prints (`What the schema now holds`) are the check that the build matched — the figures it should
print are `private 18 0` and `public 79 79`, which is what `docs/schema/schema.sql` holds today
(`grep -c '^CREATE TABLE'` by schema; 79 `ENABLE ROW LEVEL SECURITY`, all in `public`). Those counts
are **established for the tested and dumped schema and UNVERIFIED on hosted** until that step has
printed once.

The `jsonb` invariant deserves a note because it shapes how you write to this schema. `0630` added a
`<table>_<column>_json_shape` CHECK to every `jsonb` column in `public` and `private` by looping over
`information_schema.columns`, and the invariant requires every `jsonb` column added **later** to have a
constraint whose definition mentions `jsonb_typeof(<column>)`. `public.ops_settings.value` satisfies
it with a stricter check (`jsonb_typeof(value) = 'object'`). The rule this enforces is in `CLAUDE.md`:
write JSON as `${JSON.stringify(x)}::text::jsonb` or `tx.json(x)`, **never** a bare `::jsonb`
(lesson L-006).

## 13. How to build a clean database locally

Nothing below needs a credential or touches the hosted project.

```bash
# 0. Once per checkout.
cd /path/to/claudecampsophie
pnpm install --frozen-lockfile

# 1. A local PostgreSQL 16 (any PG16 works; this is the repo's helper).
pnpm db:local
# The default the harness and the dump script assume:
#   postgres://postgres:postgres@127.0.0.1:5432/postgres
# Override with DATABASE_URL if yours differs.

# 2. Build a database by hand: platform shim first, then the 44 migrations.
psql "postgres://postgres:postgres@127.0.0.1:5432/postgres" \
  -c "create database pencillift_dev;"
psql "postgres://postgres:postgres@127.0.0.1:5432/pencillift_dev" \
  -v ON_ERROR_STOP=1 -f supabase/tests/shim/supabase_platform_shim.sql
DATABASE_URL="postgres://postgres:postgres@127.0.0.1:5432/pencillift_dev" \
  pnpm --filter @pencillift/db run migrate
# prints: Applied 44 migrations.
```

The shim step is required off-platform and only off-platform: it supplies `auth`, `storage` and the
three Supabase roles. On a real Supabase project the platform provides them, so `db-migrate.yml` runs
the migrate step alone.

```bash
# 3. The authorization suite builds and drops its own databases — no step 2 needed.
pnpm test:db
# While authoring one area, apply only some migrations:
PL_MIGRATIONS_ONLY=0001,0300 pnpm test:db

# 4. Regenerate the committed DDL after any migration, in the same commit.
scripts/dump-schema.sh
# builds a scratch database, dumps public+private+app, writes docs/schema/schema.sql,
# and refuses to write a dump containing COPY or INSERT.

# 5. Everything CI runs.
pnpm check && node scripts/assert-test-count.mjs

# 6. The pre-commit gate (fail-fast, whole repo).
scripts/verify.sh
scripts/verify.sh --only api,db   # or one area
```

To rebuild from scratch, drop and repeat step 2 — do **not** re-run `migrate` against a database that
already has the schema (see §12: the set is one-shot).

Applying to the hosted project is a separate, deliberate act: GitHub → Actions → *Apply database
migrations* → Run workflow, typing `APPLY` in the confirm input, with the repository secret
`SUPABASE_DB_URL` set to the project's **session pooler** string (port 5432, not the transaction
pooler on 6543, which does not support every statement a migration uses). See
`docs/Deployment_Runbook.md` and `docs/Owner_Actions.md`; the secret's value appears nowhere in this
repository and must not.
